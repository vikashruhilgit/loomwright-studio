# 08 — Phase 2 exit check: `studio ask` creates a trigger that fires, and a Loomwright version change produces a note, in the running system

## Status: ready

**Priority:** MVP · ROADMAP phase 2 "Done when" · every phase ends with a check in the running system

**As** the owner,
**I want** phase 2's two exit conditions proven end to end, once deterministically in CI and once live on my Mac,
**so that** phase 2 is done on evidence, not on passing unit tests.

## Scope

1. **Deterministic test** (CI, no model, phase 1 stand-in session pattern): a real kernel composed with the shipped features. A stand-in Wright answers `studio ask "remind me at 17:00 to check X"` by calling `kernel_trigger_register(once, <today 17:00 local>, notify, "check X")`. With an injected clock advanced past 17:00, one notification row for that trigger exists and the stub notifier received one post with the deep link. A second test swaps the fixture `installed_plugins.json` from one contract version to another and asserts one note file and one notification.
2. **Live run (owner, on the Mac, kernel installed with `studio service install`, a real Wright model set):**
   1. `studio ask "remind me at <HH:MM, 3 minutes from now> to check X"`; record Wright's reply, `studio triggers`, the notification popping up at that minute, and the click opening Terminal on `studio notifications show <id>`.
   2. The literal sentence once: `studio ask "remind me at 5pm to check X"`; record the trigger row and, at 17:00, the notification.
   3. `studio triggers off <id>` on a third reminder before it fires; record that it doesn't fire.
   4. Version change: either a real Loomwright update during the run, or the documented fixture switch (a test `installed_plugins.json` the kernel is pointed at, with the owner's consent recorded); record the note file and the notification.
   5. `kill -9` the kernel between registering a reminder and its time; launchd restarts it; record that the reminder fires once.
3. **Evidence**: `docs/evidence/phase-2-exit-live-<date>.json` (same style as phase 1's) with each step's outcome and the commit it ran against.
4. **Docs**: `docs/ROADMAP.md` marks phase 2 done with the date and evidence link; `docs/OPEN_QUESTIONS.md` closes or updates the items items 02 and 03 probed (installed_plugins desktop-app case, host mode from Studio, notifier under launchd); `docs/ARCHITECTURE.md` "Kernel tools" lists what phase 2 shipped.

## Acceptance criteria

- [ ] The deterministic tests pass in `npm test` on CI (Linux) without a model, network or macOS notifier.
- [ ] The evidence file records all five live steps with outcomes; any step that failed is recorded as failed with findings, and phase 2 is not marked done until a rerun passes (as phase 1's first live run was).
- [ ] `docs/ROADMAP.md`, `docs/OPEN_QUESTIONS.md` and `docs/ARCHITECTURE.md` are updated as above; `bash scripts/check-docs.sh` passes.

## Validation (must pass before merge)

- `cd kernel && npm ci && npm run typecheck && npm test`
- `bash scripts/check-docs.sh`
- Owner's live run, evidence file committed; its path in the PR body.

## Risks

- The live run finds a gap (as phase 1's first did). Findings become new items in this folder's plan doc, not fixes folded into this PR.
