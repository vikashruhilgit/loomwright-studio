# 09 — Phase 3 exit check: a deterministic CI test and a live run on the owner's Mac

## Status: ready

**Priority:** MVP · ROADMAP phase 3 "Done when" · D33 (an agent may run the live check while the owner watches)

**As** the owner,
**I want** phase 3's exit criterion proven twice, deterministically in CI and live on my Mac,
**so that** "done" means it works in the running system, not just in unit tests.

## Problem

ROADMAP phase 3 is done when "a plain-English request becomes a stored playbook whose dry-run output is shown before it's enabled; dedupe key, priority and model come from the user, with Wright only proposing defaults". Items 02–08 build the parts; nothing proves the whole.

## Owner decisions (2026-10-16, binding)

- **Dry run = a read-only agent run.** The owning agent runs the playbook once in a dry-run session: read-only tools work, and every outward or persistent tool call is denied by the kernel and recorded as "would do". The result (what it would do, what the dedupe key would skip, next fire times, tokens used) is stored and shown. Tokens count against limits.
- **Storage = SQLite + a markdown mirror.** The kernel's `playbooks` table is the source of truth. A read-only markdown copy under the data dir (`memory/playbooks/<slug>.md`) is rewritten on every change so the owner can read it (invariant 8).
- **Enabling = Wright requests, the owner approves once.** Wright drafts and dry-runs, then calls `kernel_playbook_enable`, which the approval gate always holds; the owner approves or denies it in `studio approvals`, which shows the dry run. Enable is refused unless the playbook's current version has a dry run. Any edit makes a new version and returns the playbook to draft (a new dry run and a new approval). This keeps D3 and invariant 3 as they are.
- **What starts a playbook:** the existing `once` / `cron` triggers, linked to the playbook, plus a manual "run now" by the owner. Event triggers (a new PR, a ticket) wait for connectors (phase 6).
- **What a fire does:** it wakes the owning agent (Wright in phase 3; crew is phase 4) with the playbook's intent as its instruction, under the playbook's model, priority, approvals and limits.
- **Priority = `low` / `normal` / `high`.** Pending events run high first, then normal, then low; oldest first within a level.
- **In phase 3:** priority ordering, "always allow" per playbook, per-playbook token limits, and the per-playbook API-key fallback (D28).
- **Policy is the user's (invariant 1, D4).** Every policy field (dedupe key, priority, model, token limit, fallback) records who set it: `wright` (shown as "proposed") or `owner`. No playbook ships preinstalled.

## Scope

1. **Deterministic test** `kernel/test/phase-3-exit.test.ts` (a real kernel with the shipped features, a stand-in Wright, an injected clock, a stub notifier, no model): a plain-English ask → Wright (stand-in) creates a draft with proposed values → the owner sets priority and model with `studio playbooks set` → dry run stored and shown → enable held → owner approves → retry enables → the trigger fires at its instant with the playbook's model and priority → a second fire with the same dedupe key is skipped → an "always" grant lets a repeated outward call pass, and a new version asks again → the playbook's token limit parks the next fire.
2. **Live harness** `kernel/test/phase-3-exit-live.test.ts` (`STUDIO_LIVE=1` only, as phase 2's) and runbook `docs/evidence/phase-3-exit-runbook.md`: on the installed service with a real Wright, a plain-English request (a cron playbook a few minutes ahead with a tag) → draft, mirror file, dry run, enable request in `studio approvals` with the dry run shown → the owner approves → it fires at its minute → a second instant with the same dedupe key is skipped → cleanup turns off the harness's own playbooks only. Setup in the runbook includes adding the six `mcp__kernel__kernel_playbook_*` names to an existing `wright.json` tool policy (it is create-if-absent).
3. **Evidence:** `docs/evidence/phase-3-exit-live-<date>.json` in phase 2's shape, with `run_by` (D33).
4. **Docs:** `docs/ROADMAP.md` marks phase 3 done only after a live run passes; `docs/ARCHITECTURE.md` "Kernel tools" lists the phase 3 tools as built; `docs/OPEN_QUESTIONS.md` records anything the run left unverified.

## Non-goals

- Fixing what the live run finds: each finding becomes a new item in this folder's plan doc, not a fix folded into this PR.

## Acceptance criteria

- [ ] `kernel/test/phase-3-exit.test.ts` passes in CI and covers every step in Scope 1.
- [ ] Given `STUDIO_LIVE` unset, when the suite runs, then the live harness is skipped.
- [ ] The runbook lists setup (build, `service install`, Wright's model, the tool-policy names), each live step, what only the owner can see, and cleanup; `bash scripts/check-docs.sh` passes.
- [ ] After a passing live run, the evidence file and the ROADMAP ✓ land in the same commit.

## Validation (must pass before merge)

- `cd kernel && npm ci && npm run typecheck && npm test`

## Assumptions

- Phase 2's live harness patterns (run tag, session-provenance cleanup, summary file) are reused, not rewritten.

## Risks

- A real model may phrase or schedule the playbook differently from the request; the harness checks the stored row, not the reply text.
