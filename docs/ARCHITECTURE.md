# Architecture

Status: design, pre-code. Decisions referenced as D# are in `DECISIONS.md`. Q# refers to the probe-numbered technical items in `OPEN_QUESTIONS.md` (probe pN): Q1 bundled binary, Q2 subscription auth, Q3 usage reporting, Q4 plugin loading and auth isolation, Q5 session lifecycle, Q6 cap signal.

## Three layers

```
┌─ Surfaces ─────────────────────────────────────────────────┐
│  Electron app (menu bar + windows)   CLI: studio ask|status|stop │
│  Optional connectors: Slack, …                              │
└──────────────┬─────────────────────────────────────────────┘
               │ HTTP + WebSocket on 127.0.0.1, token from Keychain
┌─ Kernel (deterministic TypeScript daemon, launchd service; never an LLM) ─┐
│  Event loop · Trigger engine · Session manager · Approval gate            │
│  SQLite store · Budget meter · Audit log · Loomwright adapter             │
│  Kernel tools (in-process MCP) exposed to the brain                       │
└──────────────┬────────────────────────────────────────────────────────────┘
┌─ Brain (Claude sessions via @anthropic-ai/claude-agent-sdk) ─┐
│  Wright (lead): role + memory → plans, writes playbooks, delegates │
│  Specialists: named agents, each running Loomwright agents/commands │
└──────────────────────────────────────────────────────────────┘
```

The kernel owns everything that must be reliable: lifecycle, state and limits. The brain owns everything that needs judgement. The brain changes the world only through kernel tools, or through tool calls its permission policy allows. (D2, D5, D11)

## Data model

One SQLite database in the Studio data dir (e.g. `~/.loomwright-studio/studio.db`), with **one writer: the kernel.**

| `connectors` | id, kind, status, scopes (all optional; D12) |

| `events` | append-only audit log of everything the kernel did. Triggers refuse any update, delete, replace or explicit id, so ids always follow append order (the kill switch reads the latest by id). Opening the store refuses, with a typed error and writing nothing, a database whose `events` table or triggers are missing or altered, that has any trigger the kernel did not create (on any table or view, since one elsewhere can still write into `events`), whose `schema_migrations` versions are not a contiguous run from 1, or whose schema is newer than the kernel; it checks again after applying pending migrations |
| `budget` | usage per day, per playbook, per agent, per session. A token limit counts input + output + cache-write tokens; cache reads are recorded and shown but don't count. Read from `result.modelUsage` per model at each query's end, never per-message usage; the "≈$" estimate uses the full `costUSD` (D24, D26). `modelUsage` is cumulative per SDK session across resumes, so the kernel keeps the last totals in `sessions.model_usage_json` and writes only the delta, attributed to the kernel host's local calendar day the result arrived on; a lower total is a fresh baseline (added in full, logged), and an empty or all-zero `modelUsage` is ignored and logged so it never resets the baseline (SDK 0.3.284's `sdk.d.ts` says crash/startup-error results may carry zeroed usage; not probed live, and ignoring is the safe choice either way). Thinking tokens have their own column and are never added to the counted total (they are already inside output). An agent's daily token limit comes from the user's config (none by default); reaching it notifies once per agent-day and refuses that agent's new starts until the next day, while a running session finishes its turn. The agent limit refuses new starts only: resuming an interrupted session is not refused by it (the account cap still refuses resumes), so the limit does not bound the tokens a resumed session spends the same day |
| `work_steps` | idempotency key (unique), status (started / done / failed), result, failure reason (`interrupted`: a crash left it `started` and it was not declared re-runnable, reported as `failed:interrupted` with one notify; `error`: its work threw, unless the caller declared that error effect-free, as the loop does for an admission refusal, in which case the claim of the innermost step whose own work raised it is released and a later call runs the work again; an outer step the error only passed through records `error`, since its work may have had an effect before the inner step), and whether it was declared re-runnable, stored by the call that first started the step: that stored value, never a later caller's option, decides whether a crash leftover is run again, and it is never rewritten. A step returns its result in JSON form on the first call and on every repeat alike (a `Date` is its ISO string both times, an `undefined` property is dropped), so a redelivery sees exactly what the first delivery saw; a result JSON cannot serialize (a `BigInt`) is never stored `done`: a synchronous step rolls back, while an async step, whose effect already happened, is recorded `error` so it is not run again. Makes each kernel tool's effect happen at most once across a crash (D2). Exactly once holds only for effects inside SQLite committed in the step's own transaction; an external effect (a file, a `gh` comment) is at most once only through the key plus this check, and is re-run after a crash only when declared re-runnable (idempotent). `failed` is terminal for a key |
| `wakeups` | id, due time, reason, task, status (`pending`, `fired`, or `superseded`), fired time. Scheduled wake-ups, each fired once by id: the move to `fired` and the queued `wakeup` event commit together, so one that came due while the kernel was down fires once on the first tick after the restart. Only `pending` rows fire. The budget module's cap wake-ups (reason `cap_reset:<provider id>:<rate-limit type>` for a known reset, `cap_recheck:…` for an unknown one) are the only rows with those prefixes: `scheduleWakeup` (and so the `kernel_schedule_wakeup` tool) refuses a reason starting `cap_reset:` or `cap_recheck:`, and a supersede never touches a row with a `wakeup_scheduled` audit event. They are scheduled so at most one is pending per provider and type: scheduling a new one marks the earlier pending one (and the provider's legacy untyped `cap_reset:<id>` / `cap_recheck:<id>` rows) `superseded` in the same transaction, and a superseded row never fires or counts as pending in `/status`. A `cap_*` wake-up means "ask admission again", never "the park ended": a handler must not release parked work on it, because the park ends only when admission admits |
| `event_queue` | id, kind (`wakeup` or `message` in phase 1), payload, source ref (the unique dedupe anchor of a derived row, e.g. `wakeup:<id>`; null for a user message), status (pending / done / failed), not-before time (a parked row waits for it), attempts, last error, task, session, enqueued and done times, and a priority (default `normal`; every row queued before migration 13 reads `normal`; see [the queue](architecture/queue.md)). The loop's processing state lives here because `events` is append-only; every transition is also audited in `events` |
| `cap_state` | account (the auth provider's id, the key), rate-limit type, status, resets-at time. Subscription cap state from the SDK's `rate_limit_event`; that provider's sessions stay parked until `resetsAt` (D28). Also stores the event's utilization, the untyped `unifiedWindows` verbatim (0–1 fractions, observed live only), and a reset source: `event` (from `resetsAt`, epoch seconds stored as ISO) or `recheck` (unknown reset: a `rejected` event without a usable `resetsAt` — missing, not ahead of now, more than 35 days ahead, or past year 9999 — or a usage-limit text found via the SDK's `USAGE_LIMIT_ERROR_PREFIXES`, parked as `text_fallback` and re-checked hourly). A `rejected` window notifies and schedules a wake-up once (`notified_resets_at`); an `allowed_warning` window warns once (`warned_resets_at`). An unexpired park only ever extends (a later known reset, notified once more): an unknown or earlier reset, or an `allowed` from another session, never shortens or clears it. The one exception: a `rejected` event for the same hit as an unexpired `text_fallback` park whose reset source is `recheck` (no unexpired park of the event's own type) replaces the text-fallback row in one transaction when it carries a known reset, even an earlier one, because the hourly re-check time is a guess, not a window (a guess is read from the reset source, never the type name: `text_fallback` is reserved for the tracker, and an event naming it is stored as `unknown`); it notifies only when the known reset is later, and an event with an unknown reset leaves the text-fallback park as it is. Parks key on the auth provider's stable id, for the cap tracker and admission alike (a request naming another provider fails closed); the provider's account label is display text only (`/status` shows it as `account`, with the key as `provider`; event payloads carry both), so relabelling the account neither lifts a park nor starts a second one. Migration 9 moved label-keyed rows and pending wake-ups to the id; a label that could itself be a provider's id (any `auth_providers` id, or `api-key` / `subscription-token`) was copied to its providers and kept, never moved, so no provider lost a park. The session row's `auth_account` label is never used as a key. Admission refuses every start and resume on a parked account, including each retry attempt of a resume (a refused retry launches nothing and leaves the session `interrupted`, resumable once the park ends); nothing switches provider. The D28 API-key fallback is a config flag plus a dollar ceiling, both off by default; once playbooks exist it is read per playbook and the kernel-wide placeholder is never consulted |
| `auth_providers` | id (the provider id, e.g. `subscription-token`), account label, token creation date. Non-secret metadata only; the secret stays in the Keychain. Expiry warning 30 days before the token's one-year life ends; a `notify` event at most once per provider per UTC day (D27) |

**Memory is markdown, not the database** (invariant 8): `memory/<agent>/role.md`, `preferences.md`, `people.md`, `lessons.md`, one handoff note per task at `memory/<agent>/handoffs/<task>.md` under the data dir (`_unassigned` for a session with no agent, `session-<id>` for one with no task), plus `memory/shared/` for things every agent should know about the user. Users can read, edit and version it.

## Kernel tools (the brain's only levers)

All of these are generic mechanisms; policy is set per playbook (D3, D4). They run in-process as an SDK MCP server, which needs streaming input (Q5). Every name carries the `kernel_` prefix because in Q5 an unprefixed `task_create` lost to the built-in `TaskCreate`, while `kernel_record_task` was called correctly.

- `kernel_task_create / kernel_task_update / kernel_task_list / kernel_task_get`
- `kernel_playbook_create / kernel_playbook_update / kernel_playbook_list / kernel_playbook_disable / kernel_playbook_dry_run / kernel_playbook_enable`: the phase 3 playbook tools, added by the playbooks feature's sub-files; every `kernel_playbook_enable` call is held for the owner (see [Phase 3 features](#phase-3-features))
- `kernel_trigger_register(kind, spec, tz?, action, text, idempotency_key) / kernel_trigger_remove(id, idempotency_key) / kernel_trigger_list()`: `once` (an instant with a time zone) or `cron` (5 fields plus an IANA zone) triggers that `notify` or `wake_agent`; see [triggers](architecture/triggers.md)
- `kernel_agent_create / kernel_agent_update / kernel_agent_list / kernel_agent_message`: the phase 4 crew tools (`kernel_agent_message` ships since phase 4 item 06, see [delegation](architecture/delegation.md); the other three since item 07, see [agents: Wright's charter tools](architecture/agents.md#wrights-charter-tools)): propose a new crew member's charter or change one (every `kernel_agent_create` and `kernel_agent_update` call is held for the owner and applied by the kernel on approval), list the crew, and delegate to a member (see [Phase 4 features](#phase-4-features))
- `kernel_session_spawn(agent, task, prompt) / kernel_session_stop / kernel_session_status`
- `kernel_schedule_wakeup(at, reason) / kernel_request_stop(handoff)`
- `kernel_approval_request(action, payload, idempotency_key)`: records a `pending` approval and returns at once; the owner decides (`studio approve <id> once` / `studio deny <id>` in phase 2) and the decision arrives as a new message, so the session is never held open ([approvals](architecture/approvals.md))
- `kernel_hook_propose / kernel_hook_apply / kernel_hook_verify` (D6)
- `kernel_notify(title, body, idempotency_key)`: a notification for the owner, posted natively and listed by `studio notifications` ([notifications](architecture/notifications.md))
- `kernel_loomwright_capabilities()`: the adapter's manifest, read from Loomwright's `capabilities.json` (D13, D32)

Phase 1 ships the first six: `kernel_task_create / kernel_task_update / kernel_task_list / kernel_task_get / kernel_schedule_wakeup / kernel_request_stop`. The server is named `kernel`, so the SDK's full names are `mcp__kernel__kernel_*`; a session can call one only when the user's tool policy lists that full name (the kernel never adds them itself). Every session launches with the Agent SDK's tool deferral off, so the tools are offered directly and never only through the SDK's `ToolSearch` meta-tool, which no policy needs to list (see the Session manager section; the 2026-10-15 live run, where the gate denied `ToolSearch` and Wright could call none of its tools, is in [the evidence](evidence/phase-2-exit-live-2026-10-15.json), and the probe that settled the fix in [the tool-loading evidence](evidence/agent-sdk-tool-loading-probe.md)), and the session manager builds a fresh server for every launch attempt (an instance cannot reconnect). Tool input is untrusted data: each handler validates it and returns an error result instead of throwing. The `idempotency_key` is caller-chosen and per tool: `kernel_task_create`, `kernel_schedule_wakeup` and `kernel_request_stop` require one; `kernel_task_update` takes one optionally (without it the update runs directly, not as a work step); `kernel_task_list` and `kernel_task_get` take none. A call with a key runs as a work step keyed `<tool>:session-<session id>:<key>`: a repeat in the same session (also after a resume or a restart) returns the first result, while another session using the same key is not deduplicated against it. `kernel_request_stop` writes the handoff note (atomically; re-runnable, since rewriting it is idempotent), records `stop_requested` (once per work-step key: a crash re-run of the same call adds none, while each call with a new key adds its own), and then schedules the stop out of band instead of awaiting it from inside the session's own tool call; a stop that fails is recorded as `stop_failed`.

Phase 2 ships six more, each through its feature's contribution: the trigger tools `kernel_trigger_register / kernel_trigger_remove / kernel_trigger_list` ([triggers](architecture/triggers.md)), `kernel_approval_request` ([approvals](architecture/approvals.md)), `kernel_notify` ([notifications](architecture/notifications.md)) and `kernel_loomwright_capabilities` ([Loomwright](architecture/loomwright.md)).

Phase 3 ships six more, all through the playbooks feature's contribution: `kernel_playbook_create / kernel_playbook_update / kernel_playbook_list / kernel_playbook_disable` ([playbooks](architecture/playbooks.md)), `kernel_playbook_dry_run`, which runs a draft once in a dry-run session ([dry runs](architecture/dry-run.md#a-playbooks-dry-run)), and `kernel_playbook_enable`, which the rail always holds for the owner ([playbooks: enabling](architecture/playbooks.md#enabling)). A fresh `wright.json` proposes all six; an existing one keeps the tool policy it has, so the owner adds them ([phase 3 exit runbook](evidence/phase-3-exit-runbook.md#setup)).

Phase 4 item 06 ships `kernel_agent_message` ([delegation](architecture/delegation.md)), through the agents feature's delegate part, and item 07 ships `kernel_agent_create / kernel_agent_update / kernel_agent_list` ([agents: Wright's charter tools](architecture/agents.md#wrights-charter-tools)), through its charter-tools part. The rest of the list above is still planned.

Later items add their tools through a feature contribution (see [Phase 2 features](#phase-2-features)), never by editing the tool server.

Everything else comes from ordinary Claude Code tools (`gh`, MCP connectors, bash, Loomwright commands), limited by the agent's permission policy.

## Main loop

1. An **event** arrives: a trigger fires, the user sends a message, or a wake-up comes due.
2. The kernel logs it and checks budget and cap state. If over a limit, it parks the event and notifies; no retries (D17). The cap is detected from the SDK's `rate_limit_event` with `status: 'rejected'`, not from error text: the kernel parks that account's sessions until `resetsAt` and notifies. A playbook may opt in to continue on the user's own API key under a hard spending ceiling the user sets; without the opt-in, work waits (D28). The real `rejected` event has not been observed yet (Q6).
3. It checks the playbook's dedupe key against past work (if the user defined one) and drops duplicates.
4. It **starts or resumes** the right agent's session: resume if a task is in flight, otherwise fresh, with role, memory, the Loomwright manifest and the event.
5. The agent decides what to do: answer, create tasks, draft or edit a playbook, start specialists.
6. Outward or persistent actions go through the **approval gate**. "Always allow" is stored per playbook, never globally.
7. The session ends with `kernel_request_stop`: the kernel writes the handoff note, updates tasks, and schedules the next wake-up.

How it is built (item 07): an event is written to SQLite before anything acts on it, as an `event_queue` row plus an `event_enqueued` row in `events`, in one transaction. "Internal" events are the kernel's own audit rows in `events` (`notify`, for example): logged, never queued. Each tick fires the due wake-ups into the queue, then processes `pending` rows by priority (`high`, `normal`, `low`) and by id within a level (see [the queue](architecture/queue.md)) with handlers the caller injects; the loop has none of its own and invents no behaviour. A row is marked `done` only after its handler's effects are committed; a kind with no handler is marked `done` with an `event_unhandled` row. A handler refused by admission parks the row: it stays `pending` until `not_before` (the refusal's retry time, or an hour when unknown or not later than now, so a park never ends in the past; `event_parked` keeps the raw retry time next to the effective one), with no second notify (D17); the work step whose own work was refused is released so the redelivery runs it again, but if the refusal passed through an outer step that may already have had an effect, that step is `failed` and so is the event (with one notify), never re-run blindly. Any other failure marks the row `failed` with one notify, and the loop moves on: a failed event never blocks the queue. A work step interrupted by a crash (not re-runnable) already notified when it was marked `failed:interrupted`, so when the handler rethrows that error the loop records `event_failed` with the step's key and sends no second notify; the same holds on a redelivery after a crash between that mark and `event_failed`, when the event's step reports itself `failed:interrupted` (a `WorkStepFailedError`), while any other `WorkStepFailedError` gets the loop's notify; if the handler ran the step inside its own transaction, whose rollback undid that mark and its notify, the loop sends the one notify itself. A handler that wraps the error in its own reports a different failure and gets the loop's notify too. `start()` and `stop()` keep one timer chain: a tick still running across a `stop()` → `start()` does not reschedule beside the new chain. A crash after a handler's effects and before `done` delivers the event again after the restart, so handlers make their effects idempotent through work steps keyed on the event id.

## Session manager (Q5)

Every agent session is an SDK `query()`, never a `claude --bg` session: those belong to the CLI's own background manager and can't host kernel tools or the approval callback (Q5).

- **The kernel spawns the CLI itself** through the SDK's `spawnClaudeCodeProcess` option, each session in its own process group. The group id is recorded in SQLite before the session starts; the group leader's start time is then read with an asynchronous `ps` (never blocking the event loop) and recorded next to it once it answers, only while the row still records that group, and is null when `ps` could not read it (or the kernel died before it did). Q5 showed a `kill -9` of the kernel orphans the CLI child rather than stopping it, so without a reaper invariant 2 doesn't hold.
- **The boot-time reaper kills only a group it can prove is still the session's.** It does NOT kill every recorded group still alive: a pgid can be reused, and the owner's own interactive `claude` processes lead groups too. It kills a live group only when its leader is named `claude` AND still has the recorded start time, or when `ps` positively reports the leader gone while the group lives on (a pid is never reused while its group exists). A reused or foreign group, a row with no recorded start time, and a failed `ps` are left alone. A row becomes `interrupted` (resumable) only when its group is gone or proven foreign (another leader name or start time). A row whose group may still be the session's and alive (no recorded start time, a failed `ps`, or a kill that outlived its deadline) becomes `orphaned`, with the reason in its event: it is never resumed while that holds, and every later reap re-examines it (appending `session_reap_deferred` while nothing changes) until its group is gone, or until the owner abandons it (`studio session abandon <id>` or `POST /sessions/<id>/abandon`, allowed only while its latest orphaning reason is `leader_unverified`): it then becomes the terminal `abandoned`, with `by: "owner"` and `via` in its event and its kill flag cleared, and the kernel never signals that group, since it cannot tell it from a foreign one. `EPERM` from a kill means "not gone yet", never "foreign".
- **Every kill re-sends SIGKILL until the group is gone.** One `kill(-pgid, SIGKILL)` that races a fork misses the new child, which survives in the dead group (see `docs/OPEN_QUESTIONS.md`), and the CLI forks shells. Stop, post-session cleanup, the SDK-abort path and the reaper all re-kill every 25 ms until `ESRCH`, for up to 2 s. The kernel's own kills then record `session_kill_incomplete`; the SDK-abort listener cannot record anything and leaves a group that outlives it to the kernel's next kill. The listener is removed once the leader exits, so an abort that comes later never signals a pgid that may have been reused. A session whose group the kernel could not confirm gone ends `failed` with reason `kill_incomplete` (the intended outcome kept as `cause`), never `stopped` or `completed`, and a resume never launches another attempt over it. The one exception is `failed:auth`, written at the first auth signal (AC7) before its kill; it is never resumed either. Either way the kill that gave up (or errored) flags the row (`kill_incomplete_at`), and a later kill that confirms the group gone clears it. Every `reapOrphans` (at the latest, the next boot) retries each flagged terminal row with the same identity check and kill as an orphan, never changing its status: it appends `session_kill_retried` and clears the flag once the group is gone or proven foreign, so a row is retried only while its group may still be the session's.
- While the kernel is alive, stopping is stdin EOF, then a force-kill of the whole process group after a ~2 s grace (Q5). A stop that arrives after the session's stream has already ended (while its group is being cleaned up) still kills the group, but the session keeps the outcome its stream produced (`completed`, or `failed` with the result or stream error), with `stop_requested_after_end` in the event, not `stopped`: it was no longer running. A background-loop crash (`kernel_error`) likewise keeps an already-computed outcome in its event.
- **The SDK session id is pre-assigned** (`sessionId`), so it is recorded in SQLite before the CLI starts and a kernel killed before the first message still leaves a resumable id.
- **An auth failure surfaces within ~1 s** as an `api_retry` message with a 401, long before the CLI's own retries give up (Q4). The kernel fails the session on the first one: `failed:auth`, one notify event, no retry and no resume.
- **A session never runs in a macOS-protected folder (D31).** `startSession` and `resumeSession` refuse a `cwd` inside `~/Documents`, `~/Desktop`, `~/Downloads` or iCloud Drive (`PROTECTED_LOCATIONS` in `kernel/src/protected-paths.ts`, the same list `service install` checks; resolved through symlinks as far as the path exists, the `/System/Volumes/Data` firmlink prefix removed from both sides (realpath leaves that alias of `/Users/…` as is, yet TCC protects it the same), compared case-insensitively on a path-segment boundary) with `SessionError("protected_cwd")` naming D31, right after the `cwd` validation: before admission, auth or any spawn, so nothing is spawned and no row is written or changed. The refusal is appended to `events` as `session_refused` (`{reason: "protected_cwd", cwd}`; `session_id` null for a start, the session's id for a resume). A launchd agent can't read those folders, so such a session would fail obscurely; this is a fixed safety check, not a playbook setting.
- **A session records where it runs, and resumes only there.** `startSession` writes the cwd's realpath to `sessions.cwd` (`resolvedPath` in `kernel/src/protected-paths.ts`: the D31 check's resolution, symlinks resolved as far as the path exists and the `/System/Volumes/Data` prefix removed) in the same `INSERT` that creates the row, the `failed:auth` row's included, so a kill right after the insert still leaves it in the store; the SDK still gets the cwd as given. `getSession`, `GET /status` (each `starting`/`running` session's `cwd`) and `studio status` (escaped) show it. `resumeSession` resolves its `cwd` the same way and, when it differs from the recorded one, refuses with `SessionError("cwd_changed")` naming both paths, after the row checks and before the Loomwright read, admission, auth or any spawn: one `session_refused` event (`{reason: "cwd_changed", cwd, recorded_cwd}`, the session's id) and the row unchanged. A row from before migration 15 (`cwd` null) is not compared. The brain handler resumes an agent's interrupted session for the task in the new message's folder, so a message naming another folder now fails (`session_refused: cwd_changed: …`) instead of continuing that session elsewhere. A mechanism, not a policy: which cwd a session gets is unchanged. Read from Agent SDK 0.3.284's type docs, not probed on a live session: the CLI keeps its files per project directory (`~/.claude/projects/<sanitized-cwd>/`, its default auto-memory folder), and the SDK's session-file helpers (`listSessions({ dir })` and the rest) search every project directory when given none; whether a CLI `resume` launched in another cwd finds its transcript is not verified (tracked, with a probe, in `docs/OPEN_QUESTIONS.md`). The kernel does not depend on the answer: it refuses the other cwd either way.
- **Two observers see every SDK message of every session:** `onMessage` (the budget meter) and then `onOutput` (the console's `recordSessionOutput`, phase 5; see [Phase 5 features](#phase-5-features)). Each is called in its own try/catch: an observer that throws is recorded as one `observer_error` event naming it and never breaks the session, and one observer's throw never skips the other.
- **Every session sets `model` explicitly**, since the default is Opus (Q1); which model is playbook policy (D4).
- **Every session sets `permissionMode` explicitly** (Q5), never `bypassPermissions` (D5).
- **Every tool call passes a kernel `PreToolUse` hook callback.** `canUseTool` alone is skipped for read-only commands and for tools listed bare in `allowedTools` (Q5).
- **Streaming input.** The prompt is an async iterable; with a plain string prompt the in-process kernel tools are unavailable (Q5).
- **Kernel tools reach a session directly: tool deferral is off on every launch.** By default the bundled CLI defers MCP tools: the session sees them only through the SDK's `ToolSearch` meta-tool, which no policy lists, so the gate denies the load and the session can call none of its kernel tools (the 2026-10-15 live run). The launch env passed to `query()` therefore always carries `ENABLE_TOOL_SEARCH=false` (`TOOL_DEFERRAL_OFF` in `kernel/src/sessions/kernel-env.ts`). It is set in `#launch`, which builds the options for a start and for every resume attempt, so the two cannot diverge. It is spread last, after the auth provider's env and the Loomwright host switch, so a variable inherited from the daemon's environment cannot turn deferral back on. The name is kernel-owned: a contract whose host switch names it is refused (`loomwright_contract`, `contract_invalid`), as a credential or process-control name is, rather than silently overwritten. With it off, the CLI offers every tool from the start and no `ToolSearch`, so the policy stays exactly the user's list and the gate decides each call by its exact name; `ToolSearch` itself stays denied (`tool_not_allowed`) like any unlisted name. The cost is that every offered tool's schema is in context each turn (43 in the probe: 12 kernel tools and 31 CLI built-ins). The setting is undocumented in the SDK's types; it was probed on SDK 0.3.284 ([evidence](evidence/agent-sdk-tool-loading-probe.md)), and a later SDK may rename it: `kernel/test/sessions-tool-loading.test.ts` pins that the kernel sets it, and the opt-in live test catches the SDK ignoring it.
- Sessions run isolated with `settingSources: []` and Loomwright loaded by path (D27; see Auth).
- **Tool commands run outside the CLI's group, so the kernel tracks them (H08).** The CLI's Bash tool starts each command in a new session and process group (`docs/OPEN_QUESTIONS.md`, phase 1 live run), so `kill(-pgid)` of the CLI's group leaves it running. While any CLI runs, one manager-wide poll (every 1 s, one `LC_ALL=C TZ=UTC ps -A -o pid= -o ppid= -o pgid= -o lstart= -o comm=` snapshot at a time, asynchronous, stopped when no CLI runs) walks each CLI's descendants by parent pid and records every group other than the CLI's own in `session_groups` (migration 10): the pgid, its leader's executable (`comm`) and start time, and when it was first seen (`session_group_recorded`). A stop and the kill switch walk once more before their kill, and the reaper walks a live orphaned CLI once more (when it is proven the session's) before killing it. Every kill of a session's CLI group (stop, kill switch in both modes, natural end, crash cleanup, reaper) then kills each recorded group with the same kill-until-gone, but ONLY while `ps` shows its leader with the recorded executable and start time (same tolerance as the CLI check). Another executable or start time (a reused pgid), an absent leader (`leader_gone`) and a failed `ps` are skipped and never signalled (`session_group_skipped` with `reason`); a kill records `session_group_killed`, `session_group_kill_incomplete` or `session_group_kill_error`. The reaper kills recorded groups whatever the CLI's outcome (also when the CLI already exited: `group_gone`, `no_pgid`, `pgid_reused`), never an `abandoned` row's. A group whose kill gave up or whose `ps` failed keeps its own flag (`session_groups.kill_incomplete_at`; the session row's flag is keyed on the CLI's pgid), and every `reapOrphans` retries it, whatever the session's status, until it is killed or proven not the session's. Such a group counts as "may still be alive" exactly as the CLI's own group does: a stop, the kill switch (either mode), a natural end, a crash cleanup or a failed resume attempt that leaves one unsettled ends the session `failed` (`kill_incomplete`, with `tool_groups_unsettled: true` and the intended outcome as `cause`; a failed resume attempt launches no further attempt), never `stopped` or its clean outcome, and `/status` lists the session under `kill_unconfirmed` with the group in `tool_groups` until a reap settles it (the terminal status is kept). **Known gaps, not covered:** a tool group started after the kernel died whose CLI then exited before the restart can't be found by the reaper (nothing links it to the session any more; launchd restarts the kernel within seconds, so the window is small, not zero); a group living less than one poll interval may be missed (it is gone anyway, unless something in it outlives that); a group whose leader exits before it is first seen, or whose parent chain to the CLI is broken first (a re-parented process), is never recorded; a recorded group whose leader exits while others in it live on is skipped (`leader_gone`), not killed; a leader that `exec`s another program after the last poll is skipped as `command_differs`. Linux is not targeted: the walk and check also run on Linux procps (CI), but nothing there is verified beyond that.
- Resume is by SDK session id from the on-disk transcript. Treat it as retryable and record the error text (Q5). Before launching, a resume re-checks the recorded group exactly as the reaper does and refuses (`not_resumable`, the row becomes `orphaned`) while it may still be the session's and alive, so two CLIs never run the same SDK session.
- The CLI binary is bundled in the SDK's per-platform package; the packaged app keeps it outside the asar archive or passes `pathToClaudeCodeExecutable` (Q1).

## Safety kernel (fixed; D5)

- **Per-agent permission policy.** Wright is read-mostly. Builders write only in git worktrees. Reviewers comment only: the owner lists every outward category but `gh_pr_comment` in a reviewer's `never` list, and the kernel denies a call in one outright, never as an approval ([approvals: the never boundary](architecture/approvals.md#the-never-boundary)); the kernel ships no `never` list as a default. No agent ever gets `bypassPermissions`. A Bash prefix allowlist matches at word boundaries and refuses shell control and substitution characters, BUT allowing a program that runs other programs grants arbitrary execution through its arguments: for example `find` (`-exec`), `xargs`, `env`, `git` (aliases, `-c`, hooks), `npx`, `npm` (scripts), `sed` (`e`/`w`), `awk` (`system()`), `sh` and `bash`. The kernel adds no blocklist for them, because the policy is the user's (invariant 1): listing such a prefix is a decision to allow whatever it can run.
- **Kernel-side SDK hook callbacks the brain can't edit**, passed as a `PreToolUse` callback on every tool call (Q5):
  - block `gh pr merge` outside Loomwright's sanctioned gate
  - block pushes to protected branches
  - block writes to kernel files and to global settings without approval
  - phase 2 builds this as a fixed rail after the policy decision ([approvals](architecture/approvals.md)): `gh pr merge` is denied outright (`merge_blocked`), writes to the kernel's own files are denied outright (`protected_kernel_path`), a Bash command the rail will not read (an unusual control or space character, or past its size bounds) is denied outright, and every recognised `git push`, the listed gh writes and every write to global settings or hooks are held as a pending approval the owner decides once
- **Untrusted input is data.** PR bodies, comments and ticket text reach the model as quoted data. There's an injection test in the roadmap.
- **A worked-on repo's `AGENTS.md` is untrusted input too.** The CLI's builtin `agents-md` plugin loads even with no plugins configured and puts that file into the model as project instructions where the repo has no `CLAUDE.md` (invariant 3, Q4).
- **Budget ceilings.** Per day, per playbook and per agent, plus a limit on concurrent sessions. Fails closed: park and notify.
- **Kill switch.** `studio stop --all` / the menu-bar button aborts every session, and no trigger fires while it is engaged. Durable: its state is derived from the append-only `events` log (`kill_switch_engaged` / `kill_switch_released`), so no restart (launchd KeepAlive) can silently release it, and the daemon does not start the event loop while it is engaged. `POST /stop-all` engages it, stops the loop (the current event finishes, no other starts), then stops every live session through the session manager, killing its CLI's group and every tool group recorded for it (H08, see the session manager) (`stopped`; a group that cannot be confirmed gone, the CLI's or a recorded tool group, ends `failed`/`kill_incomplete`; a session that already ended `failed:auth` gets its groups' kill now and is reported `failed:auth` only once they are all confirmed gone or proven not the session's, otherwise `stop_failed` (`kill_incomplete`), its row or tool group flagged for the reaper) and records `stop_all_completed` with each outcome. An outcome carries `ended_on_its_own: true` when the session had already ended before the stop (its stream had ended, for example `failed` with a result error, or it was already `failed:auth`) and the stop settled its groups; a pending auth kill timer is cancelled by that stop. `studio stop --all` reports such a session as already ended (as it does a `completed`, `interrupted` or `failed:auth` outcome from an older daemon), and exits non-zero unless every session is confirmed stopped or ended (a session not confirmed stopped stays listed under `/status`'s `kill_unconfirmed` while its row or one of its recorded tool groups is flagged), and waits for the answer longer than one session's worst-case stop (stop grace + group-kill deadline + leader-exit wait, plus a margin; `status` and `resume` wait 5 s); if it still times out it says the kill switch may already be engaged; `POST /resume` (`studio resume`) releases it and restarts the loop. Triggers: nothing fires while it is engaged (the loop does not run, and the triggers' due work checks it too); after the release, a trigger's instants that fell inside the engagement are recorded `missed_kill_switch` and never fired (see [triggers](architecture/triggers.md)).

## Loopback API

- **127.0.0.1 only**, never `0.0.0.0`/`::`: the host is a constant, not a setting. The port is OS-assigned and written with the daemon's pid to `<dataDir>/api.json` (mode 0600; never the token). A graceful stop removes the file only while it still names that pid.
- **Bearer token from the Keychain item `loomwright-studio-api`** (account `loomwright-studio`), 32 random bytes as hex, generated by the kernel on first start. It is written with `security -i` reading `add-generic-password …` on **stdin**, so the secret never appears in `argv`; without `-U`, so an existing item is never overwritten. `security -i` can exit 0 when its inner command failed, so the kernel reads the item back and trusts only that.
- **Authentication before routing:** every request, whatever its path or method, needs `Authorization: Bearer <token>` (constant-time compare). Otherwise `401 {"error":"unauthorized"}`; only after that are unknown paths 404 and wrong methods 405. Phase 1 routes ignore request bodies; a contributed route (see [Phase 2 features](#phase-2-features)) receives the parsed JSON body, at most 1 MiB (`413 {"error":"body_too_large"}` beyond), and malformed JSON gets `400 {"error":"invalid_json"}`; its answer always has a JSON body, so a status without one (1xx, 204, 205, 304, or outside 200-599) is a `500 {"error":"internal_error"}` instead.
- **Routes:** `GET /status` (kernel version, uptime and pid; kill switch; each auth provider's health, one of `ok | missing | invalid_shape | expiring(days) | error(reason)` and never a secret, computed at the request's one instant; `starting`/`running` sessions; `kill_unconfirmed`: every session, whatever its status, whose CLI's group a kill gave up on or errored on (`kill_incomplete_at` set) or that has a recorded tool group still flagged and unsettled (H08, listed in `tool_groups` with its pgid, executable and flag time; not for an `abandoned` row, whose groups are never signalled again), and may still be alive, until the reaper confirms it gone; `orphaned`: every `orphaned` row with its pgid and latest orphaning reason from the kernel's own events; pending queue rows and wake-ups; today's counted tokens per agent (D26); `cap_state` per account), `POST /stop-all`, `POST /resume` (see the kill switch above), `POST /sessions/<id>/abandon` (the owner's abandon of a `leader_unverified` orphan, see the session manager above: 400 `invalid_id` for an id that is not a safe positive integer, 404 `not_found`, 409 with the refusal's stable code such as `not_abandonable`; the POSTs run one at a time, and an abandon whose client has disconnected before its turn, such as the CLI giving up behind a slow `stop-all`, is skipped with nothing written; the `studio` CLI asks for confirmation first unless given `--yes`, refuses without a terminal, and on a timeout or a connection lost after connecting says the session may or may not be abandoned and to run `studio status`).
- **The live feed** (`GET /events/stream`, phase 5): one WebSocket on the same server, behind the same token. Node never sends an `Upgrade: websocket` request through the request handler, so the server's `'upgrade'` listener authenticates it first, with the same constant-time check: a missing or wrong token gets a raw `401 {"error":"unauthorized"}` with `WWW-Authenticate: Bearer` and the socket is closed, never upgraded. Only then is the path checked: any path but `/events/stream` is `404`, and a method other than `GET` on it `405`, both closed, never upgraded. An authenticated feed upgrade is handed to `handleEventFeed(socket, req, {store, now})` in `kernel/src/api/feed.ts`, which today closes it at once with 1013 and the reason `not yet`; item 02 builds the feed ([feed](architecture/feed.md)). Closing the API terminates every open feed socket, so a feed never holds a graceful stop open.
- **`studio` CLI** (`status [--json]`, `stop --all`, `resume`, `session abandon <id> [--yes]`; plus `service install|uninstall`, which need no running daemon; install's start check then reads the new kernel's `api.json` and the Keychain token under the same rules, and additionally requires `api.json`'s pid to be the job's pid from `launchctl print`): reads `api.json`, checks its pid is alive (`kill(pid, 0)`; `ESRCH` or `EPERM` mean "not running") before it reads the token or sends anything (`session abandon` asks for confirmation between that pid check and the Keychain read; `--yes` skips the question, and with no terminal and no `--yes` it refuses at once with exit 2), and only ever connects to `127.0.0.1`. Residual risk: after a `kill -9` of the daemon, if the OS reuses both that pid (for one of this user's processes) and the port (for another local listener), the CLI would still send the token there. The pid check narrows this case but doesn't close it; launchd restarting the daemon (item 09) rewrites `api.json` on start. Later items add subcommands through a feature contribution (see [Phase 2 features](#phase-2-features)), dispatched after the same pid check and before the Keychain read.
- **Graceful daemon stop** (SIGTERM/SIGINT): close the API, stop the loop, stop every session in `shutdown` mode (the same kill as a stop, but a running session ends `interrupted` with `kernel_shutdown`, resumable after the restart, so a graceful stop never loses more than a `kill -9` would; a group that cannot be confirmed gone is handled as in the kill switch and left flagged for the next boot's reap), remove `api.json`, close the store.

## Phase 2 features

Phase 2 adds five features, each in its own directory under `kernel/src/` and each documented on its own page: [Loomwright](architecture/loomwright.md), [notifications](architecture/notifications.md), [triggers](architecture/triggers.md), [approvals](architecture/approvals.md) and [the brain](architecture/brain.md). Migration 11 creates their tables (see the data model). Every value set in them is checked in code, not by SQL, and the item that builds a feature validates its own values.

Each feature exports one `FeatureContribution`: a name plus optional tools, routes, subcommands, event handlers and due work. The kernel merges every shipped contribution (these five, then phase 3's playbooks, phase 4's agents and phase 5's console) once at start, before the store opens. Each ships only what its own item has built (so far the Loomwright tool and version watcher, the notifications feature, triggers' agent tools, owner controls and due work, the approvals tool, routes and subcommands, and the brain's `message` handler, `POST /ask`, `GET /messages/:id`, `GET /messages`, `studio ask` and `studio messages`; no trigger or approval is preinstalled, see [triggers](architecture/triggers.md) and [approvals](architecture/approvals.md), and no model is chosen for Wright, see [the brain](architecture/brain.md)) and no playbook or policy, so nothing is preinstalled (invariant 1).

- **Tools** join the kernel MCP server, built per launch like phase 1's. A name must start with `kernel_`, and the shape must be a zod raw shape (every value a zod schema), checked at start rather than at each launch; arguments are checked against that shape (a bad one is an error result, never a throw); the handler gets the phase 1 tool context plus `stepKey(idempotencyKey)`, which returns the `<tool>:session-<id>:<key>` work-step key, and its value is returned as JSON text (a value that is not JSON is an error result).
- **Routes** are matched after authentication and after phase 1's routes, by method and an exact path or one with `:param` segments. The handler gets the params, the query and the parsed JSON body (see the Loopback API), plus the kernel's store and clock (contributions are merged before the store opens, so this is how a route reads its feature's tables), a read-only view of the kill switch (`killSwitch.state()`, always set; it can't engage or release it), and, when the API server was given the kernel's session manager, that manager (`sessions`; absent in a composition without one), so a route can stop a session (phase 5), and the API server's one POST queue (`serialized(fn)`, the queue phase 1's stop-all, resume and abandon run on; optional in the type but always set by the API server), through which a route runs a short, bounded change to session or kill-switch state so it never interleaves with theirs (never a wait, which would delay the kill switch; see [session control](architecture/session-control.md#the-post-queue-seam)). It answers a status and a body that the API always sends as JSON (a string becomes a JSON string; a body that cannot be serialized is a 500). The status must be an integer 200-599 that carries a body: a 1xx, 204, 205, 304 or anything outside that range is a 500 instead, with nothing of the answer sent. Every such 500 (a handler throw, a body that is not JSON, an invalid status) answers only `{"error":"internal_error"}` and appends one `route_failed` event naming the contributor, the route's method and declared path, and the clipped error, the same way as `due_work_failed`; a failed write never changes the 500.
- **Subcommands** join the `studio` CLI, each with a one-line help appended to its usage. They run after the `api.json` pid check and before the Keychain read, and call the API through an authenticated client. A phase 1 command word never depends on the contributions: `studio stop --all` and `studio service uninstall` run even when the contributions cannot be merged, after one warning line saying why.
- **Event handlers** are keyed by an existing event kind (`wakeup` / `message`); any other kind refuses the start with `UnknownEventKindError`. They merge with the handlers the caller injects.
- **Due work** runs once per loop tick, after the due wake-ups fire and before the queue. Each function runs in its own try/catch: a throw appends one `due_work_failed` event naming the contributor, and the tick goes on.

**Every tool's shape must serialise through the Agent SDK.** A session gets the kernel tools through the SDK's own `tools/list`, and one input schema the SDK's bundled serialiser cannot convert fails the whole list: every session is then offered no kernel tool while the server still reports `connected` (the 2026-10-19 phase 4 live exit, where `kernel_agent_create`'s `z.record` charter did this, is in [the evidence](evidence/phase-4-exit-live-2026-10-19.json)). The kernel's own zod conversion accepts such a shape, so the rule is checked through the SDK itself: CI lists every shipped tool with a real MCP client against the server the sessions get (`kernel/test/tools-sdk-list.test.ts`), and `startKernel` runs the same listing once before the store opens, refusing the start with an `InvalidContributionError` (a permanent start failure) naming each tool whose schema fails (the phase 1 tools, and no contributed tool, when the phase 1 tools fail to list alone; every contributed tool when none fails alone and only their combination does), or each tool a listing that succeeds leaves out. A free-form JSON object is declared the way `kernel_approval_request`'s `payload` is (an object check with `type: object` as its JSON Schema), never as `z.record`.

**Collisions refuse to start; nothing is silently overridden.** Two owners of the same tool name, subcommand name or handler kind, or of two routes with the same method whose paths overlap (an exact path or a `:param` pattern that some request path matches both), make `startKernel` reject with `ContributionConflictError`, naming both owners, before the store opens. A phase 1 tool, subcommand word or injected handler counts as an owner, and a contributed route whose path overlaps a phase 1 route is refused whatever its method (phase 1 routes match first and would shadow it). A malformed part (a bad name, path, method, help line or tool shape, a part that is not a function or a list) is an `InvalidContributionError`. The daemon treats `ContributionConflictError`, `UnknownEventKindError` and `InvalidContributionError` as permanent start failures, so launchd does not restart a kernel that would fail the same way. The `studio` CLI merges against the same phase 1 tool names, routes and command words as the daemon (one list, `PHASE1_RESERVED`), so it refuses the same collisions and malformed parts the daemon refuses to start, with three daemon-only refusals: a kind in the handlers a caller injects into `startKernel` is a daemon-only owner, and `approvalApplierOf` and the Agent SDK listing check (`assertKernelToolsList`) run only in `startKernel`, so the CLI still runs (for example `studio stop --all`) over a composition one of them refuses. In the CLI, a collision or a malformed contribution reached for a contributed (or unknown) word prints one line naming the owners and exits 1; a phase 1 word first prints that same line once as a warning (`studio: warning: …`), so the owner learns why the daemon refuses to start, then runs as in phase 1.

## Phase 4 features

Phase 4 adds one feature, agents, in `kernel/src/agents/`, registered as the seventh contribution (`agentsContribution`, after playbooks). As with playbooks, each phase 4 item builds only in the sub-file it owns, and each sub-file exports one part listed in `AGENT_PARTS` (its tools, routes, handlers, and verbs of the one `studio agents` subcommand), merged in that order with the same collision rules. With no verb, `studio agents` prints its help; the roster's verbs (item 02: `list`, `show`, `create`, `rename`, `set`, `off`, `on`) are on [agents](architecture/agents.md).

Migration 14 creates the `agents` table and adds `brain_messages.from_agent` / `depth` / `reply_to` / `workspace` (see the data model). Every value set is checked in code, not by SQL, and no crew member ships preinstalled (invariant 1).

The shared readers every item uses: `readAgentSettings` reads `config/agents/<id>.json` (Wright's `wright.json` included); a crew member's file may carry the optional enforced `never`, `limits` and `workspaces` (a workspace may not be in a macOS-protected folder, be or be inside the data dir by any spelling, or contain it by any spelling, `/System/Volumes` included through the firmlink), and an unknown key in it (at the top level or in `tool_policy`, so a misspelt `never` too) is `settings_invalid` naming the key, never dropped, while Wright's file refuses `never` and `workspaces` as `settings_invalid` until an item applies them to Wright's sessions (its `limits` are read: the budget applies `tokens_per_day` and `sessions_at_once` at admission, see `docs/architecture/budget.md`, and `kernel_agent_message` applies `delegation_depth`, see [delegation](architecture/delegation.md#wrights-delegation_depth)); `ensureAgentMemoryFiles` creates a crew member's memory files under `memory/<id>/` but never its charter (`role.md`); and the read-only registry lookups (`getAgent`, `listAgents`, `isRoutable`). A crew id matches `^[a-z][a-z0-9-]{0,31}$` and is never one of the kernel-owned `memory/` folders (`KERNEL_MEMORY_DIRS`: `wright`, `shared`, `_unassigned`, `playbooks`), since it names `memory/<id>/` and `config/agents/<id>.json`; `RESERVED_AGENT_IDS` is that list, so a playbook mirror can never be read as a charter.

A session policy may carry `never`: categories from the closed `NEVER_CATEGORIES` list in `kernel/src/sessions/policy.ts` (one per outward form the rail emits, such as `git_push`, `gh_pr_comment` or `settings_write`), refused `invalid_params` otherwise. The session gate asks `boundaryDecision` about every outward call before the dry-run branch and before any hold or grant; a call in a `never` category is denied `agent_boundary` with its category, never held and never covered by a grant ([approvals: the never boundary](architecture/approvals.md#the-never-boundary), step 5 of the rail).

`kernel_agent_create` and `kernel_agent_update` are in the fixed outward set (`ALWAYS_HELD_TOOLS`) and in `KERNEL_APPLIED_ACTIONS`: every call is held as a pending approval, an "always" grant may never cover one, and the kernel applies the owner's `once` itself. The agents feature's charter-tools part registers the applier (phase 4 item 07): on the owner's `once` the kernel creates or changes the crew member itself ([agents: Wright's charter tools](architecture/agents.md#wrights-charter-tools)).

The crew is documented on [agents](architecture/agents.md), delegation on [delegation](architecture/delegation.md). The items that change approvals, budget, the brain and playbooks document that on [approvals](architecture/approvals.md), [budget](architecture/budget.md), [the brain](architecture/brain.md) and the playbook pages.

## Phase 5 features

Phase 5 adds the desktop app and the kernel mechanisms it needs. Item 01 (the foundation) ships only seams and stubs, so each later item edits only its own module, test and page; no behaviour beyond the stubs ships with it.

**The console feature.** `kernel/src/console/` is registered as the eighth contribution (`consoleContribution`, after agents). As with playbooks and agents, each item builds only in the sub-file it owns, and each sub-file exports one part listed in `CONSOLE_PARTS`, merged in this order with the same collision rules: `events.ts` (item 02), `output.ts` (item 03), `control.ts` (item 04), `pause.ts` (item 05) and `threads.ts` (item 06). A part may also add `studio` verbs through its optional `subcommands` field, merged in part order like its routes. Today three parts are filled: the events part's `GET /events` route (item 02, see [the event feed](architecture/feed.md)), the output part's `GET /sessions` and `GET /sessions/:id/output` routes and its `studio sessions` subcommand (item 03, see [session output](architecture/session-output.md)), and the control part's `POST /sessions/:id/stop` and `POST /sessions/:id/kill` routes (item 04, see [session control](architecture/session-control.md)); `pause.ts` and `threads.ts` are empty, so the contribution is its name, those five routes and that subcommand, with no tools, handlers or due work. The CLI's `studio session stop` and `session kill` are verbs of the built-in `session` command word, parsed in `kernel/src/cli/index.ts`, that call control's routes, not contributed subcommands. Like every feature module, nothing it loads may import the Agent SDK, the session manager or `kernel.ts` as a value, because the `studio` CLI loads it (`feature-seams.test.ts`'s module-graph pin); `output.ts` imports the SDK's message type only as a type.

**The seams it gives later items:**

- **`session_output`** (migration 16, see the data model), with its kinds closed in code as `SESSION_OUTPUT_KINDS` (`kernel/src/console/output.ts`). The session manager calls `onOutput` for every SDK message (see the session manager), and `kernel.ts` wires it to `recordSessionOutput(store, sessionId, message)`, which was a no-op until item 03 filled it in.
- **Route controls.** A contributed route's request carries `killSwitch` (read-only) and `sessions` (the kernel's `SessionManager`, when the API server was given one) beside the params, query, body, store and clock (see [Phase 2 features](#phase-2-features)), so a console route can stop one session without reaching into the server. Item 04 added `serialized`, the API server's one POST queue (always set by the server, optional in the type), so a route's acceptance of a stop never interleaves with the kill switch, resume or abandon ([session control](architecture/session-control.md#the-post-queue-seam)).
- **The feed's upgrade** (see the Loopback API): authenticated before any upgrade, only on `GET /events/stream`, handed to the `handleEventFeed` stub.

**The app** (`app/`: Electron, React, TypeScript and Vite) runs as two halves, and the API token lives only in one of them:

- **The main process** (`app/electron/`) owns the window, the menu-bar tray and `loomwright-studio://` deep links (stubs until item 17), and the one connection to the kernel (`kernel-connection.ts`). That connection does what the `studio` CLI does: it reads `<dataDir>/api.json` (pid and port, never a token), checks the pid is alive, reads the bearer token from the Keychain item `loomwright-studio-api` through `/usr/bin/security`, and connects only to `127.0.0.1`. It makes every API call and relays the feed, calls only routes listed in the contract (`not_in_contract` otherwise: a param is URL-encoded, a param that is exactly `.` or `..` is refused, and the URL's parsed path must equal the filled contract path before the token is sent), and never logs the token or returns it to the renderer.
- **The renderer** (`app/src/`, React) runs sandboxed, with `contextIsolation: true` and `nodeIntegration: false`. Its only way out is the preload, which exposes exactly one key, `api` (the `StudioBridge` type), through `contextBridge.exposeInMainWorld`. Every method crosses to the main process over IPC; no channel, `ipcRenderer` or Node API reaches the renderer, and so no code path in it can read the token. With no kernel answering it shows the "kernel unreachable" band, and with no `api.json` the terminal setup steps (setup stays in the terminal).
- The only test seam is in the main process's environment (`STUDIO_DATA_DIR`, and a fixture token honoured only in an unpackaged run), which Playwright's `electron.launch({ env })` sets for the fixture kernel. The renderer can't reach it.
- `npm run package` builds a local, ad-hoc-signed `Loomwright Studio.app` that registers the `loomwright-studio://` scheme. It is never published or notarised ([package evidence](evidence/phase-5-foundation-package.md)).

**The contract.** `app/src/api/contract.ts` types every route the app calls (the existing phase 1, brain, notifications, approvals, triggers, playbooks and agents routes, plus the routes items 02-06 add), the feed's frames and the bridge, and lists the routes as `CONTRACT_ROUTES`. The kernel's routes are the truth: each kernel item makes its route match the contract. `kernel/test/console-contract.test.ts` reads the file as text (the kernel never imports the app package) and pins the route list, that every route the contract marks existing is one the kernel serves, and that the contract's session output kinds equal `SESSION_OUTPUT_KINDS`.

## Auth (D15, D16, D27, D29)

- A pluggable provider interface: `subscription-token`, `api-key` (Keychain); `bedrock`, `vertex` later (D16).
- **`subscription-token`** (D15, D27): a long-lived token the user creates with `claude setup-token` in their own terminal, read from the macOS Keychain item `loomwright-studio-oauth` and passed to each session as `CLAUDE_CODE_OAUTH_TOKEN`. Sessions run fully isolated: `settingSources: []`, Loomwright loaded by path, nothing else of the user's (D27, proven in Q4). Studio never runs a login flow of its own (invariant 6).
- The `subscription-token` provider strips `ANTHROPIC_API_KEY` from the child environment, because a key wins over the token and would silently move billing to the API (D27, Q2).
- Every provider builds the child environment through one strip list (`kernel/src/auth/credential-env.ts`): every `ANTHROPIC_*` variable, the other credential and provider-switch variables, the CLI's OAuth and bridge endpoint switches (`USE_LOCAL_OAUTH`, `CLAUDE_BRIDGE_BASE_URL` and the rest), and its API endpoint switch `CLAUDE_CODE_API_BASE_URL`, any of which could send the token to another host; whether the public CLI honours the OAuth and bridge switches is unverified (`docs/OPEN_QUESTIONS.md`), and they are stripped anyway. A provider's `health()` never throws: a Keychain failure, an invalid clock or an unreadable creation date is `error` with a reason (`keychain_unreadable`, `clock_unreadable`, `token_created_at_unreadable`), never `ok`.
- The token lasts one year; the kernel checks for expiry and notifies before it lapses (D27). Token entry checks the prefix and length before saving, since a cut-off token fails with a 401 (Q4).
- **Personal build only.** The `subscription-token` provider is compiled out of any distributed build, which supports only API keys and 3P providers (D29).
- `api-key` sets `ANTHROPIC_API_KEY` from the Keychain (Q2); it's also the per-playbook opt-in fallback at the cap (D28). The API-key path is stub-tested until a commercial launch (D16).
- **The kernel runs as a per-user launchd agent** (item 09, D11) **from an install copy** (H07, D31). `studio service install` (macOS only) first copies the built kernel (`dist/`, `package.json` and the production `node_modules` derived offline from `package-lock.json`: every non-dev entry present on disk) to `<dataDir>/app/<kernel version>/`, through a temporary sibling dir renamed into place (a same-version copy is renamed aside, replaced, then removed; a failed copy leaves the existing one intact), and the plist runs that copy's `dist/daemon.js`, never the checkout's: a launchd job can't read a macOS-protected folder (`~/Documents`, `~/Desktop`, `~/Downloads`, iCloud Drive; TCC answers `EPERM`), where a checkout may live. An install target inside one (`PROTECTED_LOCATIONS`, `kernel/src/protected-paths.ts`, after symlink resolution and with the `/System/Volumes/Data` firmlink prefix removed, case-insensitive) is refused with one line naming D31 before anything is copied, written or loaded; installing from an installed copy is refused too; a `node` under a version manager's dir (`~/.nvm`, `~/.volta`, …) gets a one-line warning. It then writes one plist, `~/Library/LaunchAgents/com.loomwright.studio.kernel.plist`, and loads it with `launchctl bootstrap gui/<uid>`; `studio service uninstall` boots it out and removes that file. Nothing else in `LaunchAgents/` is read or touched. The plist runs the built `daemon.js --launchd` with the absolute `node` path, `RunAtLoad`, `KeepAlive` = `{SuccessfulExit: false}` and `ThrottleInterval` 60: launchd restarts the kernel after any non-zero exit, at most once a minute, and never after exit 0. `--launchd` only changes the daemon's exit statuses (`kernel/src/daemon-exit.ts`; started by hand, every failure still exits 1). Under launchd, a start failure a retry can't fix (the store lock held by another kernel; a refused store open, because the store failed its integrity check or its schema is newer than this kernel; a bad argument; an auth provider not in this build) exits 0 and is not restarted; every other start failure (a Keychain read, the API token, any other store failure) exits 1 and is retried at most once a minute; a crash or `kill -9` is restarted the same way; a graceful SIGTERM stop exits 0, and if its teardown throws the error is logged and the exit is still 0, so it is not restarted. Every failed exit writes one line naming its cause, and whether launchd restarts, to `kernel.err.log`. `install` over a loaded agent boots it out (a `bootout` exit status 36, EINPROGRESS, is taken as an unload still in progress, not a failure; unverified, `docs/OPEN_QUESTIONS.md`), then polls `launchctl print` (at most 5 s) until it is gone; still loaded after 5 s, it fails with one line saying to run it again and never bootstraps (the new kernel would find the old one still holding the store lock, a failure that is not restarted). It then runs `bootstrap`, retried once on exit status 5; a launchctl failure reports its exit status and the first line of its stderr. **Start check:** loaded is not running, so install then polls (every 250 ms, at most 15 s) until the new kernel answers `GET /status` with 200: `launchctl print` must report the job's `pid`, `api.json` must name that same pid (a stale `api.json` from the previous kernel never counts), the pid must be alive, the API token must be in the Keychain (on a first install the new kernel creates it), and the answer must name that pid; until the deadline anything else is "not up yet". This is the only place `launchctl`'s stdout is read: `print`'s, bounded to 1 MiB, parsing only `pid =` and `last exit code =`. On success it prints the kernel version and install path, and only then removes older versions under `<dataDir>/app/`. On failure it prints the last probe's reason, the `last exit code`, the last 20 lines of `kernel.err.log` (plus a hint to answer a waiting Keychain prompt with Always Allow and re-run, when that tail shows a Keychain failure), boots the agent out and removes the plist so launchd can't restart it in a loop or at the next login (the install copy and the data dir are kept), and exits non-zero. The deadline is checked between probes; one probe's Keychain read can't be interrupted (at most 10 s), so a hung read can run past it once. `uninstall` also removes `<dataDir>/app/`, never the logs or the store. stdout and stderr go to `<dataDir>/logs/kernel.{out,err}.log`. Its environment holds only `STUDIO_DATA_DIR` (always the absolute data dir its logs go under, so the daemon uses the same dir the install chose) and, when set, `STUDIO_AUTH_PROVIDER`, never a token: credentials are read from the Keychain at start. Still open (owner, `docs/OPEN_QUESTIONS.md` "Phase 1 exit: live run"): that the Keychain reads work under launchd without a terminal (Q2).

## Loomwright adapter (D13, D32)

- Resolves the **active** install from `~/.claude/plugins/installed_plugins.json`, never the newest folder in the cache (observed for CLI installs on 2026-10-06; the desktop-app case and the file's stability are unverified, see `docs/OPEN_QUESTIONS.md`). Beware: the desktop app and the CLI install plugins in different places, and `~/.claude/plugins/cache/` can hold many stale versions.
- Reads Loomwright's published, versioned `capabilities.json` (D32): the contract schema version, agents, commands and skills, result schemas, hooks and what each one writes, and the host switch that stops repo-writing hooks from writing into the session's repo (`LOOMWRIGHT_HOST_MODE=1`, with state under `LOOMWRIGHT_HOST_STATE_DIR`; contract schema 1). It doesn't parse Loomwright's manifest, frontmatter or `hooks.json`.
- Requires a minimum contract version.
- Tolerates fields it doesn't know, and reports a version change rather than breaking.
- When the version changes, compares the changelogs and tells the user about new features, offering playbooks for them (D13).
- Reads Loomwright's structured outputs only.
