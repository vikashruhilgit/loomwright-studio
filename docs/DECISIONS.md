# Decisions

These are the owner's settled decisions from the founding design session (2026-09-26 → 28). Each entry records what was decided, why, and what was rejected. Don't reopen them without new evidence; if you do, add a new entry that supersedes the old one rather than editing it.

| # | Decision | Why | Rejected |
|---|---|---|---|
| D1 | **Feasible; build it.** An always-on partner with memory, a task table, self-managed sessions, schedules and hooks | The CLI already has native background sessions (`claude --bg`, `attach/logs/stop/rm`, `claude agents --json`, `--resume`, `--session-id`, verified on v2.1.283); the Agent SDK adds in-process custom tools, hook callbacks and abort; Loomwright already has run locks, smart resume and run files | — |
| D2 | **The LLM never owns its lifecycle.** A deterministic kernel daemon owns start/stop/kill, scheduling, and state; Claude sessions are short-lived workers | A single long-running session gets compacted and forgets its commitments; nothing can wake itself from zero | "One eternal session that manages itself" |
| D3 | **Nothing predefined.** The kernel provides mechanisms (tasks, playbooks, triggers, sessions, memory, approvals); Wright authors every playbook, schedule, trigger and hook from plain English, dry-runs it, and asks for approval | Owner requirement: "I want it to have the capability, and set everything up based on user requirements" | Shipping built-in PR-review or ticket playbooks |
| D4 | **Mechanism vs policy.** The kernel ships generic mechanisms (e.g. a per-playbook dedupe key, priority, model setting). All policy is user-defined per playbook; Wright only *proposes* defaults | Owner correction: "these things should be user-defined" (about "one review per head commit") | Hard-coded dedupe/model/priority defaults |
| D5 | **Fixed safety kernel** that the brain can't edit: permissions per role, approval gate for outward/persistent actions, budget ceilings, protected kernel files, kill switch | If the agent could write its own limits, a bad instruction or a prompt injection in a PR body could remove them | Letting the agent manage its own rails |
| D6 | **Hooks in three layers:** kernel-side hooks for the partner's own sessions (fixed rails); Claude Code hooks for the user's sessions (project scope by default, global only with approval); event triggers for playbooks. Every hook change goes propose → approve → apply with backup → **verify it actually fires** → record | Loomwright incident: command hooks printing `{"ok":false}` were silent no-ops for months; `\|\| true` neuters blocking hooks | Writing hooks without a firing check |
| D7 | **Model it on Grok Bot, and improve on it.** Named persistent agents, routines, skills learned from use, a chief-of-staff lead with specialists, allow-once/always/deny approvals | Owner: "check how Grok Bot works, I want something like that" (see `research/GROK_BOT.md`) | — |
| D8 | **Multiple agents with identities.** One lead (Wright) you talk to, plus a roster of named specialists created on demand, each with its own role, memory, permissions, integrations and budget; each a real security boundary. Start small (lead + 1–2) | Owner asked for Grok-style identities; separate boundaries fix Grok's shared-VM weakness; too many agents adds coordination cost | A fixed agent set; one shared credential pool |
| D9 | **A GUI app with no compromise on UI.** Design comes first: design system + hi-fi mockups approved by the owner before any code; keyboard-first, ⌘K palette, native macOS feel, WCAG AA, designed empty/loading/error states, a polish gate per screen | Owner: "one of the best UIs, no compromise" | UI as an afterthought |
| D10 | **Electron** for the app shell, kept deliberately thin; the UI is React and talks to the kernel over a loopback API | Consistent Chromium rendering; Tauri's WKWebView is tied to the macOS version and has open production transparency/vibrancy issues; Tauri's size and RAM wins matter less because the always-on work runs in the separate kernel daemon. Switching shells later costs days, not a rewrite (see `research/ELECTRON_VS_TAURI.md`) | Tauri (revisit for mobile or wide distribution); native SwiftUI (macOS-only, slower to iterate) |
| D11 | **The GUI is not the partner.** Closing or crashing the app never stops the kernel; the kernel runs as a launchd service | Schedules and playbooks must keep running | Kernel embedded in the app process |
| D12 | **Integrations are optional connectors** (GitHub, Slack, Jira, Linear, email, any MCP). Studio works with none; a playbook that needs one asks to connect it | Owner: "Slack and GitHub identity shouldn't be mandatory" | Required Slack bot / GitHub account |
| D13 | **Always current on Loomwright via runtime grounding, not training.** A Loomwright adapter reads the installed plugin (`plugin.json`, `commands/`, `agents/`, `skills/` frontmatter, `CHANGELOG.md`, `RESULT_SCHEMAS.md`), builds a capability manifest for every session, compares changelogs on version change, and tells the user about new features. It reads Loomwright's structured outputs (`RESULT` blocks, `.supervisor/automate/*.md`, session logs, `floor.json`), never its prose. Proposed Loomwright follow-up: publish a machine-readable `capabilities.json` per release | A model can't be retrained per release; reading at runtime knows new features within minutes | Hand-maintained Loomwright knowledge in prompts |
| D14 | **Name: Loomwright Studio** (the app) + **Wright** (the lead agent: a wright is the master craftsman who owns the workshop). Specialists are its crew and can be renamed in the app. Fallback name: Clotho | A wright owns and directs the work; the name sits inside the owner's brand, so no external clash (see `research/NAMING.md`) | Treadle, Weft, Shuttle, Skein, Twill, Norn, Bobbin, Heddle, Selvedge, Reeve, Seneschal, Ariadne, Metis, Pronoia, Fate, LoomBot (clashes); Ergane (owner: "means worker, not owner") |
| D15 | **Billing: Claude subscription** for the owner's personal build, chosen knowingly over an API key | Owner decision; no API spend wanted for now | — |
| D16 | **Commercial-ready by design.** Auth is API-key-first *in code* (plus Bedrock/Vertex later); Studio never offers claude.ai login; the API-key path is stub-tested only until a commercial launch; local-first data | Agent SDK docs: third-party products may not offer claude.ai login "unless previously approved"; SDK use falls under Anthropic's Commercial Terms | Building the product on subscription login |
| D17 | **Cap-aware on the subscription.** Detect the "You've hit your weekly limit · resets …" error → park non-urgent work until the reset, notify, never retry-loop. Priorities, dedupe keys and model choice are user policy (D4) | The weekly cap is shared with the owner's own sessions and CI reviews (tripped 2026-09-15) | Retrying against the cap |
| D18 | **Dogfood first, commercialise later.** The owner uses it daily before any launch | Real daily use is the best evidence of value | Building for a market first |
| D19 | **License: PolyForm Shield 1.0.0** for Studio *and* Loomwright (Loomwright relicensed in PR vikashruhilgit/loomwright#289; its PyPI `vikashruhil-mysql-mcp` package stays MIT). Anyone may use it, including at work; only the author may commercialise it. Permanent, with no automatic conversion to open source | Owner: "people can use it but not commercialise it; only I can" | MIT / Apache-2.0 (allow resale); FSL (converts to Apache after 2 years); PolyForm Noncommercial (bans use at work) |
| D20 | **Public repo** with an "early development — not ready for use" notice; no releases or builds until the owner says so | Public repos get free GitHub Actions minutes on standard runners; Shield protects the commercial rights | Private repo (2,000 free minutes/month on GitHub Free; macOS runners ~10× the Linux price) |
| D21 | **TypeScript** for the kernel and UI, on `@anthropic-ai/claude-agent-sdk` | Machine has Node 22.14; Python is 3.9.6 (too old for the Python SDK); Loomwright's SDK spike found that the TS SDK bundles the Claude Code binary | Python |
| D22 | **Crew members are general-purpose and defined by a charter**, never a preset. A charter is identity, persona, duties, tools, boundaries, model and limits, stored as `memory/<agent>/role.md`; Wright drafts it from a sentence or the user fills it in. Code is the first domain, not the only one: a PA, a social-media manager and a work tracker are legitimate crew | Owner (2026-09-28 design review): "we only focused on code related things"; D3 already forbids predefined behaviour, so role presets were a mistake in the first mockup. Consequence: Calendar, Mail and social connectors join the roadmap after GitHub; the employment-IP question in `OPEN_QUESTIONS.md` must be answered before a work-tracking agent touches employer systems | Role presets (Reviewer / Builder / Researcher) |
| D23 | **Avatar identity: sea creatures stitched from thread.** Each crew member is a creature (shark, seahorse, octopus, turtle, jellyfish, fish, crab) drawn as embroidery in its own hue, with a loose thread end that carries the kernel state; **Wright is the crowned whale**. No faces beyond a knot for the eye | Owner rejected a blob-with-eyes construction as indistinguishable from Grok Bot, asked for a Loomwright identity ("thread or border line"), a crown for Wright, and animals. The thread end lets state be shown without a face and without motion (reduced-motion safe) | Blob with two eyes; spools and a shuttle (kept in `docs/design/avatar/` history as an alternative set) |
| D24 | **Limits are tokens per day and sessions at once, per agent.** Dollars appear only as "≈ at API rates" estimates and never as a control on the subscription build | Owner: "how is this budget going to work if we will be using subscriptions". The kernel cannot meter money on a subscription (D15); it can count tokens and sessions and detect the cap (D17). On an API-key build the same fields become real spend | A dollar budget per day |
| D25 | **Sidebar: Chat is always the thread with Wright; Crew is one thread per specialist; Team is where agents are configured.** Wright never appears under Crew | Owner tried a single "Chat" group of threads and asked for the earlier layout back. One place to talk to each agent, one place to configure them | A group of threads including Wright; Crew rows that opened Team |
