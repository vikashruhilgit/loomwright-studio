## Technical: verify, don't assume

Each of these needs a probe of the real SDK or CLI, with the finding recorded.

- [x] **Does the Agent SDK load installed Claude Code plugins** *(auth for isolated sessions decided in D27 and proven 2026-09-30, see the last bullet)* (Loomwright's agents, commands, skills, `hooks.json`) for SDK sessions? The current SDK docs list "Plugins: load by local path" and "Skills, commands, and memory: load from `.claude/` and `~/.claude/`". Loomwright's spike (SDK 0.3.202) marked hooks.json firing and skills preload/memory as NEEDS VERIFICATION. **Yes, loading and hooks both work (verified 2026-09-29, SDK 0.3.284, Loomwright 15.108.4; `probes/p4a-plugin-inventory.mjs`, `p4b-plugin-hooks.mjs`, `p4c-settings-vs-auth.mjs`).**
  - **Loading.** Default options load the user's whole setup: every installed plugin (Loomwright and others) with Loomwright's 14 agents, 42 skills and 62 commands. `settingSources: []` or `['project']` load no installed plugins. `settingSources: []` plus `plugins: [{type: 'local', path}]` loads Loomwright alone, complete. Agent types appear doubled-prefixed (`loomwright:loomwright:code-reviewer`).
  - **Hooks fire.** With `includeHookEvents: true` the SDK emits `hook_started`/`hook_response` messages with exit code and outcome. One Bash-using query fired exactly the hooks `hooks.json` defines for those events: SessionStart ×2, PreToolUse(Bash) ×1, PostToolUse(Bash) ×4, Stop ×1, all exit 0. Hooks also fire on failure (StopFailure logged an auth error). **Not exercised:** SubagentStop (Loomwright's 14 validators; needs a real Loomwright subagent) and SessionEnd (its matchers expect CLI exit reasons an SDK session does not produce). Side effect to plan for: Loomwright's SessionStart hook writes `.claude/settings.local.json` into the session's working directory, i.e. into every repo an agent works in.
  - **Conflict found: subscription auth requires the `user` setting source.** With `settingSources` of `[]`, `['project']` or `['local']`, every call fails with "Failed to authenticate: OAuth session expired and could not be refreshed", reproducibly, while `['user']` and the default succeed, and the CLI reports the login healthy (`claude auth status`: loggedIn, `oauth_token`). But `'user'` is exactly what loads the user's other plugins, global hooks and permissions into agent sessions, which the fixed safety kernel (invariant 3) should control. So on the subscription the kernel cannot yet have both the login and an isolated session. Candidate fixes, none verified yet: (A) keep `['user']` and override what leaks through a higher-precedence `--settings` layer (disable other plugins, pin permissions); (B) a long-lived token from `claude setup-token`, kept in the Keychain and passed as `CLAUDE_CODE_OAUTH_TOKEN`, with `settingSources: []` and Loomwright by path; (C) a Studio-owned `CLAUDE_CONFIG_DIR`. B is the cleanest if it authenticates; it needs a probe run by the owner, because the token is a real credential (`probes/p4d-token-isolated-auth.mjs`; its `--baseline` mode confirmed on 2026-09-29 that the owner's plan serves Fable 5.1, Opus 5.5, Sonnet 5 and Haiku 4.5 through the normal login, each answered by the requested model; the token's own model access is undocumented and still to be run). **An API key is not affected by the conflict:** with `settingSources: []` and a deliberately invalid `ANTHROPIC_API_KEY`, the CLI selected the key (`apiKeySource: ANTHROPIC_API_KEY`) and reached the API (`401 API key is invalid`) instead of the OAuth error; so the D16 API-key path supports fully isolated sessions (success itself not yet run with a real key). Using a key for the personal build would reverse D15 (API billing) and needs a new decision. Also observed: the invalid key took over 60 s to surface because the CLI retries first, so the kernel needs its own timeout and must treat auth failures as park-and-notify (D17), not wait on them. **Considered and ruled out for the personal build: Workload Identity Federation** ([docs](https://platform.claude.com/docs/en/manage-claude/workload-identity-federation)). Federated tokens act as a service account in a Claude Platform (API) organization with "the same" rate limits and usage attribution "as an API key", i.e. API billing, not the subscription (D15); and they need an OIDC identity provider issuing the workload a JWT (AWS, GCP, Entra, GitHub Actions, Kubernetes, Okta), which a laptop daemon does not have. It is the right fit for the commercial API path (D16) and the phase 10 always-on cloud host, where it removes the static API key from the VM; the bundled CLI 2.1.284 contains the federation variables (`ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_IDENTITY_TOKEN_FILE`, `ANTHROPIC_SERVICE_ACCOUNT_ID`), not yet exercised.
  - **D27 proven (2026-09-30, owner's run of `probes/p4d-token-isolated-auth.mjs`).** With a `claude setup-token` token as `CLAUDE_CODE_OAUTH_TOKEN`, `settingSources: []`, Loomwright by path and `ANTHROPIC_API_KEY` removed, all four models answered, each by the model requested: Fable 5.1, Opus 5.5, Sonnet 5, Haiku 4.5. `apiKeySource` reads `none` for the token (the same as for the normal login, so the kernel can't tell them apart from the init message), and every call carried a `rate_limit_event` (`allowed/five_hour`), so cap detection (Q6) works on the token. Loaded plugins: `loomwright` plus two **CLI builtins** that load even with no plugins at all (`path: "builtin"`): `agents-md`, which loads a repo's `AGENTS.md` as project instructions where it has no `CLAUDE.md`, and `telemetry`, the CLI's own. Nothing of the user's leaked in. Phase 1 follow-ups: treat a worked-on repo's `AGENTS.md` as untrusted input that reaches the model (invariant 3), and decide whether to turn off the CLI's non-essential traffic. Setup lesson: the first attempt failed with `401 OAuth access token is invalid` because the token, wrapped by a narrow terminal, was saved cut off at 59 characters. Studio's token entry must check the prefix and length before saving.
- [x] **Does the TS SDK bundle the Claude Code binary**, so a fresh install needs no separate Claude Code install? **Yes (verified 2026-09-29, SDK 0.3.284, macOS arm64; `probes/p1-bundled-binary.mjs`).** The CLI ships as a native 216 MB `claude` executable in a per-platform optional dependency (`@anthropic-ai/claude-agent-sdk-darwin-arm64`, and siblings for darwin-x64, linux x64/arm64 incl. musl, win32 x64/arm64), version 2.1.284, which the SDK finds with `require.resolve`. With `PATH=/usr/bin:/bin:/usr/sbin:/sbin` (no `claude` anywhere) the SDK started it and reached the CLI's init message in 620 ms. Consequences: (1) the packaged app must keep that binary outside Electron's asar archive (`asarUnpack`) or pass `pathToClaudeCodeExecutable` explicitly, since the SDK README warns `require.resolve` fails inside single-file bundles; (2) it adds ~216 MB per platform to the app; (3) the bundled CLI version moves with the SDK pin, not with the user's own `claude`. Also seen in the init message, for later items: the default model is Opus (`claude-opus-5-5`), so the kernel must always pass a model explicitly (D4), and installed plugins are reported (Loomwright 15.108.4).
- [x] **Subscription auth from the SDK.** Confirm the SDK picks up the machine's existing Claude Code login for the personal build, without any Studio login UI. **Yes (verified 2026-09-29, SDK 0.3.284; `probes/p2-subscription-auth.mjs`).** In a clean environment (`env -i` with only `HOME`, `USER` and a PATH with no `claude`) and no `ANTHROPIC_API_KEY`, a one-turn Haiku query succeeded; the init message reports `apiKeySource: "none"`, i.e. the CLI's own stored login, found through `HOME`. No login UI is involved, so invariant 6 holds. **Precedence:** with `ANTHROPIC_API_KEY` set, the init message reports `apiKeySource: "ANTHROPIC_API_KEY"`: the key wins. Consequences for the auth provider: the `subscription` provider must remove `ANTHROPIC_API_KEY` (and any other key variable) from the child environment, otherwise a stray key in the user's shell silently moves billing to the API; the `api-key` provider sets it from the Keychain. Not yet checked: that the login is reachable when the kernel runs as a launchd agent rather than from a terminal; do that once in phase 1 before relying on it.
- [x] **Cap-hit signal.** The exact error or message the SDK surfaces when the subscription weekly limit is hit, so the kernel can park until the reset. **A structured signal exists, so the kernel does not need to parse text (types read from `sdk.d.ts`, SDK 0.3.284; the healthy path was checked live on 2026-09-29 on the normal login with `probes/p6-cap-signal.mjs`; the cap-hit path itself was not triggered).**
  - **`rate_limit_event` messages.** `{type: 'rate_limit_event', rate_limit_info: {status: 'allowed' | 'allowed_warning' | 'rejected', rateLimitType: 'five_hour' | 'seven_day' | 'seven_day_opus' | 'seven_day_sonnet' | 'seven_day_overage_included' | 'overage', resetsAt, utilization, overageStatus, …}}`. Live, a one-turn call emitted one event: `status: allowed`, `rateLimitType: five_hour`, `resetsAt: 1790698800` (epoch **seconds**; 2026-09-29 16:20 UTC), and an extra field not in the types, `unifiedWindows` (`five_hour` and `seven_day` utilization as a **0–1 fraction**, 0.01 and 0.07, each with its own `resetsAt`). The kernel should treat `status: 'rejected'` as "cap hit": park every session on that account until `resetsAt`, and notify (D17). `allowed_warning` can drive an early warning.
  - **Assistant `error` field.** An assistant message carries `error?: SDKAssistantMessageError`, whose values include `'rate_limit'`, `'billing_error'` and `'authentication_failed'`. `'rate_limit'` alone does not separate a spent cap from a transient 429, so park only on a `rejected` event, and otherwise retry with backoff.
  - **Text fallback.** The SDK exports `USAGE_LIMIT_ERROR_PREFIXES` at runtime (marked `@alpha`). It lists the error-text prefixes that mean a limit was really reached, starting with `"You've hit your"`, which matches the real 2026-09-15 message "You've hit your weekly limit · resets 6am (UTC)". Use it only when no event arrives.
  - **Remaining quota, for the D24 meter.** `Query.usage_EXPERIMENTAL_MAY_CHANGE_DO_NOT_RELY_ON_THIS_API_YET({skipBehaviors: true})` returned the plan windows live: `five_hour` utilization 1 and `seven_day` 7, as **0–100 percentages** (the event uses 0–1), each with an ISO `resets_at`. So the subscription's remaining quota *is* readable, which corrects the earlier assumption in the usage-reporting item that nothing exposes it. The API is explicitly unstable, so it is display-only, never a gate. `subscription_type` came back `null` even though the windows were available.
  - **Not verified:** the `rejected` event on a real cap hit, which can't be triggered on purpose without spending the weekly limit; watch for it at the next natural cap hit and record it. Whether the `setup-token` token (D27) also receives these events; `p4d` now prints them.
- [x] **Usage reporting.** Does the SDK result's `usage` accumulate per query or report the last turn only? Is `total_cost_usd` per query? (Carried over from the spike's live checklist.) This now also gates D24: per-agent token limits need a reliable per-session token count from the SDK, and the kernel must sum it itself since nothing exposes the subscription's remaining quota. **Answered (verified 2026-09-29, SDK 0.3.284, Haiku 4.5; `probes/p3-usage-reporting.mjs`).** On a three-turn query (two Bash calls, then an answer): (1) `result.usage` is **cumulative for the query**: its input, cache-creation and cache-read counts equal the sum of the three API calls exactly (26 / 7,788 / 48,986). (2) The `usage` on each streamed assistant message **under-reports output** (4, 1, 2 output tokens against 281 in the result), so it must not be summed. (3) `result.modelUsage` (per model) is the **most complete** figure: in both queries it reports ~900 more input tokens than every visible call combined (955 vs 26; 907 vs 10, the latter for a one-turn "OK"), consistent with the CLI making auxiliary model calls that never appear as messages; its output also includes thinking tokens (`thinkingTokens`). (4) `total_cost_usd` is **per query**, not carried over within a process (second query $0.0030 after a first of $0.0229), and equals the sum of `modelUsage[*].costUSD`, labelled `costBasis: "list"`: an API-list-price estimate, i.e. D24's "≈" figure. Consequences for the budget meter: record `modelUsage` per model at each `result` message (all four token kinds plus thinking, and `costUSD` as the estimate) and sum per session, agent and day; never sum per-message usage. **Decided (D26):** a token limit counts input + output + cache-write tokens; cache reads are recorded and shown separately but do not count.
- [x] **Background sessions.** Whether the kernel should drive `claude --bg` sessions or SDK `query()` sessions, or both. Decide in phase 1 from a probe. **Answer: SDK `query()` only (probed 2026-09-29, SDK 0.3.284, CLI 2.1.284; `probes/p5-session-lifecycle.mjs`).**
  - **Why not `claude --bg`:** its sessions are owned by the CLI's own background manager and are listed by `claude agents` together with all of the user's personal sessions (24 at probe time); they cannot host in-process kernel tools or an in-process approval callback. `--bare` mode, the CLI's isolated mode, never reads OAuth, so it cannot run on the subscription.
  - **Kernel tools work in-process.** An SDK MCP server tool (`createSdkMcpServer`) ran inside the calling process (same PID). Two conditions: in-process MCP needs **streaming input** (an async-iterable prompt; with a plain string prompt the tool was not available), and tool names must not resemble built-ins (a tool named `task_create` lost to the built-in `TaskCreate`; `kernel_record_task` was called correctly).
  - **The approval gate works, with conditions.** With `permissionMode: 'default'` set explicitly, `canUseTool` was asked for `Bash touch gated.txt`, denied it, and the file was not created. It is **bypassed** by: (a) the user's `defaultMode: auto` when `settingSources` includes `'user'` (the classifier approves first; another reason for D27's isolation); (b) any tool listed bare in `allowedTools` (the SDK warns `CLAUDE_SDK_CAN_USE_TOOL_SHADOWED`); (c) read-only commands such as `echo`, which ran without the callback even in default mode. Because reads can still reach sensitive files, the kernel should gate with a `PreToolUse` hook callback, as the SDK recommends, and always set `permissionMode` explicitly.
  - **`kill -9` of the kernel orphans the session, it does not stop it.** After killing the parent mid-tool-call, the CLI child kept running: it made two more model calls, started a background shell job that outlived it, ended its turn about 5 s later, and exited. That contradicts invariant 2 ("a kill -9 at any point loses at most the current step") unless the kernel reaps orphans. The SDK's `spawnClaudeCodeProcess` option lets the kernel spawn the CLI itself: put each session in its own process group, record the group in SQLite before it starts, and on boot kill any recorded group still alive. While the kernel is alive, stopping works normally (stdin EOF, then force-kill after a ~2 s grace).
  - **Resume works.** Resuming the killed session by id continued the same session from its on-disk transcript, and the model recalled the command it had run. One earlier identical resume attempt failed with an error lost in the SDK's minified stack output; the retry succeeded. Treat resume as retryable and record the error text in phase 1.
