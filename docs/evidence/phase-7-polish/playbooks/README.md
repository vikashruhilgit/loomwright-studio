## Deviations from the mockup

Each is deliberate. Deviations 1 to 4 are recorded in `docs/DESIGN.md` (open points 6 and 8); deviations 5 to 9 are recorded here only.

1. **Per-field Set, not one batched "Save as vN+1"** (`playbooks-edit`, `playbooks-edit-refused`). The owner's only write, `POST /playbooks/:id/set`, takes one `{field, value}` per call and writes one version per call, so each of the five editable fields has its own Set. A Set that changes nothing writes no version (the kernel answers `changed: false`). The view names the version the kernel answered with and never predicts "v4". The mockup's two-fields-changed DiffView and its "enabled playbook becomes a draft again" note are not shown before a save for the same reason: nothing is staged.
2. **Name, intent and effort are read-only** (`playbooks-edit`, `playbooks-edit-refused`). No owner write route exists for them and this item adds no kernel behaviour, so they carry "Change this with Edit in English" instead of an editor. The mockup's refused-state examples for an empty name and an empty intent therefore cannot occur; the refusal shown is the dedupe key the kernel's closed set rejects, in the kernel's words rather than the mockup's local validation text.
3. **The off-state switch shows the held approval** (`playbooks-waiting`, `playbooks-detail`). On to off sends `POST /playbooks/:id/off`. Off to on sends nothing: no owner route turns a playbook on, so the switch reveals the pending `kernel_playbook_enable` approval and links to Approvals, or says the playbook turns on when Wright asks and the owner approves. The approval stays the only way a playbook turns on.
4. **`mode: live` is disabled** ("not available yet"), as the mockup shows; `draft` is the only offer (phase 6 refuses live).
5. **Tokens today is the kernel's own figure, without "≈ at API rates"** (`playbooks-populated`, `playbooks-waiting`, `playbooks-unreachable`, `playbooks-detail`). The list's Tokens today column reads `tokens_today` for the playbook's slug from `GET /budget/usage?days=1`, against the playbook's own `token_limit_per_day` ("38.2k of 200k", "0 of 50k"); a playbook with no limit shows the figure with "no limit set". The compact figure is the mockup's `tk` without a trailing ".0" and with an "M" tier. A slug the answer does not list reads "unknown", never 0. No dollar figure appears anywhere, so the mockup's "≈ at API rates" line under the figure is left empty. The detail's Tokens block is unchanged: it sums the counted tokens of the runs it lists ("N tokens counted in the last 3 runs") beside the limit per day, and a run still running reads "not counted yet", never a guess. The mockup's today meter in the detail is not built.
6. **Last run and Tokens today are read per playbook, and the last answer is kept** (`playbooks-populated`, `playbooks-unreachable`). Each cell comes from its own read; while one is in flight a cell says "reading…". Refused while the kernel answers, it says "unknown · could not be read". While the kernel does not answer, each cell keeps its last answer with the caption "last known" (in the Last run cell this stands in for the run's kind and status, which the mockup's unreachable view does not mark per cell), and a cell that never had an answer says "unknown · last known: none". The last answers are held per bridge, so they survive going to another screen and back while the kernel is away, and every read repeats when the kernel returns, so the cells show its current figures with no remount. A value nobody set reads "not set".
7. **The intent keeps the mockup's two-line clamp in the list** (the whole intent is in the detail); no other cell is truncated, and the poll spec and dedupe key are shown in full.
8. **"Ask Wright for a playbook" stays in the screen's toolbar row, not the title bar** (`playbooks-populated`, `playbooks-waiting`, `playbooks-unreachable`). The mockup puts the action beside the count line in the title bar. The shell's `Titlebar` has no actions slot, and `app/src/shell` is outside this item's lanes, so the button sits in a row above the table, right-aligned. The count line and the slug are in the title bar's subtitle slot as the mockup draws them.
9. **At the window's 900 px minimum the table scrolls sideways** (`playbooks-populated`). Eight fixed-width columns and a 160 px name column are wider than the 620 px the window leaves beside the 240 px sidebar, and the mockup is drawn wider. The name column keeps its floor instead of collapsing, and Model and Tokens today stay on one line (checked by the spec at 900 px). The shots are taken at 1180 px, where nothing scrolls.

## How to regenerate

```sh
cd app
npm ci
node node_modules/electron/install.js   # once, if the Electron binary is missing
npm run build
PLAYBOOKS_EVIDENCE=1 npx playwright test e2e/playbooks.spec.ts --workers=1
```

With `PLAYBOOKS_EVIDENCE=1` the test deletes every PNG in this folder, then writes the 20 above (the whole folder is rewritten, so every PNG whose pixels moved is committed with the item); without it the shots go to Playwright's per-test output dir, so a plain run never dirties these files. The test "the evidence README lists every screenshot, and nothing else" fails if this table, the spec's states and the files in this folder drift apart. The other tests in the spec press real keys and clicks and check what the kernel is sent (one `/set` per Set with no optimistic update, the kernel's refusal under its field, the On switch never turning a playbook on, Run now, Edit in English, the kernel going away and coming back with no remount, leaving the screen and returning while it is away, the title bar's count line and slug, the owner's avatar and name, the Schedules & triggers button, every chip at its row's right edge in both themes, the buttons' icons, the shared crumb's focus round trip, one-line Model and Tokens today at 900 px, the live feed updating rows in place) and WCAG AA contrast in both themes.
