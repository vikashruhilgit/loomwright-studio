# Integrations: Jira and ClickUp connect, the App upgrade and the repo policy card (phase 8)
Screenshots of the Integrations screen's phase 8 views, in light and dark (36 files), taken from the built app (`app/dist`, `app/dist-electron`) against the fixture kernel ([`app/e2e/fixture-kernel.ts`](../../../../app/e2e/fixture-kernel.ts) with the canned data in [`app/e2e/fixtures/integrations.ts`](../../../../app/e2e/fixtures/integrations.ts)). They are captured by [`app/e2e/integrations-phase-8.spec.ts`](../../../../app/e2e/integrations-phase-8.spec.ts), launched only through `app/e2e/electron-harness.ts`, so every window is hidden. No real account, repo, token or browser was involved: `shell.openExternal` is replaced in the main process before any click, and every name (`studio-fixture/*`, `mcp.jira.example.test`, `mcp.clickup.example.test`, `auth.example.test`) is invented. Dates are relative to the moment of capture. Each window is resized to 1180×1140 CSS px and the shots are taken with reduced motion. They are evidence for the owner's review, not visual-regression baselines: the spec never compares pixels.

The approved design is [`docs/design/mockups/phase-8.html`](../../../design/mockups/phase-8.html) (its views are named in the table), and its own screenshots are in [`docs/evidence/phase-8-mockup/`](../../phase-8-mockup/README.md).

## How they were produced

```sh
cd app
npm ci
node node_modules/electron/install.js   # once, if the Electron binary is missing
npm run build
PHASE8_POLISH_EVIDENCE=1 npx playwright test e2e/integrations-phase-8.spec.ts --workers=1
```

With `PHASE8_POLISH_EVIDENCE=1` the spec writes the PNGs here, after deleting any PNG in this folder it no longer names (the switch is shared with the other phase 8 polish folders, each writing only its own). Without it the shots go to Playwright's per-test output directory, so a plain run never dirties these files, and a test asserts no file here is newer than the run's start. Each shot is a full-window screenshot taken with `data-theme="light"` and then `data-theme="dark"` set on `<html>`, after checking that the ground colour differs between the two. The last tests check that this README, the spec's list of states and the folder name exactly the same 36 files.

## What the spec checks besides the screenshots

| Area | Check |
|---|---|
| Connect (R1) | One `POST /connectors/mcp/<kind>/connect` per press, the wait carries the answer's `expires_at`, and the recorded `shell.openExternal` address is exactly the `authorize_url` the fixture kernel answered (the main process opens it only because it remembered the kernel's answer). Open again reopens the same address with no second connect. Cancel calls `…/connect/cancel` once, and a fresh press is a fresh window with its own address. An event alone is not success: the screen reads `GET /connectors` again and shows what the row says |
| Connected (S1) | The workspace, the tools in the row's order, and each tool's grant for Mason from his `GET /agents/mason` `settings.content.connectors[<kind>]` |
| Disconnect (S1) | The confirm is first: nothing is sent while it is open or after Cancel, and one `POST …/disconnect` follows its Disconnect |
| Refusals (S1) | `authorization_denied` and `window_expired` have their own sentence, any other non-2xx connect answer (`connect_in_progress`) the generic sentence plus its code, and a refused connect opens nothing. The kernel's `message` is shown as characters beside the code, never as an element |
| Upgrade (R2, S2) | The upgrade shows for a `needs_permissions` App, its button opens exactly the `url` the kernel returned, and an address the kernel never answered is refused through the renderer's own bridge. When a later `GET /connectors` reads the App `connected` the pane returns to the connected App's detail with the window the same (no reload) |
| Policy (R3, R4, S3) | `GET /repos/policy` is read when the pane is first opened. Accept sends exactly one `POST /repos/policy/<owner>/<repo>` with `{kind, required}` of the proposal; Re-detect sends one detect; each preset sends one POST (N validated). Where GitHub cannot protect the repo there are exactly the three ways on and no preset, the two links open `https://github.com/<owner>/<repo>/settings` and `https://github.com/settings/billing/plans` with no POST, Trust unprotected sends nothing until a confirm and then sends `{kind, trust_unprotected: true}` with the picked preset, and Safe mode sends nothing |
| Nothing connected (R5) | The GitHub empty state and its Connect choice are as before, Jira and ClickUp list as not connected with one Connect each, the repo policy area reads "No repos reached yet.", no request is sent by looking, and the upgrade address is never read |

## Departures from the mockup

- **The consent and refusal views are panes, not dialogs.** The mockup draws `jira-connect`, `jira-consent` and `jira-refused` as dialogs over the pane. The app shows the waiting and the refused views in the connector's own pane (the dialog is kept for the Disconnect and Trust unprotected confirms), so the list row can follow the attempt (`connecting · waiting for you`). The mockup's `jira-connect` explainer dialog is not built: Connect starts the window directly.
- **No "Read" / "Changes things" badge on a tool.** `McpConnection.granted_tools` carries names only, so the tools table shows no badge the contract cannot back.
- **Wright's per-tool grant is not shown.** Wright has no detail route, so its cells read "Not granted" only where the roster says it does not hold the kind, else "Unknown", and the note under the table says Wright's per-tool grant is read in Team.
- **The Account and Server rows are not shown.** `McpConnection` has no account field, and the workspace is its one `server_url`.
- **The App upgrade has no permission table.** The mockup's "Now / After you accept" table is not drawn: `GET /connectors` carries the permissions the App holds now and the contract has no "after" set. The connected App's permission list stays under the upgrade section.
- **The proposal is the kernel's, not Wright's.** The mockup headed it "Wright's proposal"; the card heads it "Proposal" and says Studio read the repo's protection and proposes it, because the suggestion is made by the kernel from the detection (item 08), never by an agent.

## Limits

- The vendors' real authorize hosts and the system-browser hand-off are unverified; the fixture uses `auth.example.test`. The kernel-answered rule needs no host list, and the live ClickUp run in the phase 8 exit verifies it. Jira stays stub-only.
- The `docs/evidence/phase-6-polish/chat-cards/` PNGs are rewritten by `app/e2e/chat-integrations.spec.ts` on every run; they are not part of this folder.
